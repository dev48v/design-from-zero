⌨ Roving tabindex — a toolbar is one tab stop, not one per button. The engine is a keyboard state machine, not a browser: an abstract item list, a reduce(state, key), and an exhaustive walk of every reachable state over 240 enumerated item configurations and 79,968 key events, so every figure below is a count. 🔴 The number that matters is not how fast the arrows are — it is the number the widget adds to the page’s tab order. Across item counts 1…50 the roving widget contributes 1 tab stop at every single size; the default markup — every button focusable, which is what you get by writing no code at all — contributes 50 at 50 items, and 1,275 summed across the sweep against the roving widget’s 50. 🔴 Over the walk the invariant “exactly one item carries tabindex="0"” held 80,208 of 80,208 times and the active item was a disabled item 0 times — including the configurations where the first item is disabled, the last item is disabled, and every item but one is disabled. 🔴 And the third option, aria-activedescendant, ties roving on that headline number at 1 tab stop. It is not a worse answer, it is a different one: DOM focus never moves, so :focus never fires on the item and the element the browser thinks is focused is never the element the user is on.

Tab is for moving between widgets. Arrows are for moving inside one. That sentence is the whole pattern, and the only mechanism it needs is this: exactly one item carries tabindex="0", every other item carries tabindex="-1", and the arrow keys move which one that is. The page scores the three implementations on what a keyboard user actually pays — keystrokes — and on whether the invariant survives every key you can press.

1. The cost is linear in a number nobody chose

Put ten buttons in a toolbar and write no tabindex at all. All ten are focusable, because buttons are. A keyboard user who does not want the toolbar now presses Tab ten times to get past it, and hears ten stops where the design has one control. Nobody decided that. It is the default, and it scales with a number — how many buttons the toolbar happens to have — that has nothing to do with how many things the toolbar is.

2. The invariant is one line, and it is the whole correctness story

Exactly one item has tabindex="0". Not “usually one”. If it is ever zero, Tab skips the widget entirely and the user can never get in. If it is ever two, the widget has quietly grown a second tab stop and the bug is invisible to everyone using a mouse. Every arrow key, Home, End, Escape and every typed letter has to preserve it, from every reachable state — which is a thing you can check by walking them all rather than by trying a few.

🔴 The second row is the one that catches real bugs: the active item is never a disabled item. It is easy to satisfy on the happy path and easy to break at the edges — the first item disabled, the last item disabled, everything disabled but one. Those cases are in the walk by construction, not by luck.

3. Wrap is not a preference, it is a different algebra

With wrap=false the ends are absorbing: arrow past the last enabled item as many times as you like and you stay on it. With wrap=true the moves form a cyclic group over the enabled items — one ArrowRight per enabled item returns you exactly where you started, from every starting point. Both are identities, so both are testable as equations rather than as screenshots.

Reversibility is the third identity: ArrowRight then ArrowLeft returns to the same index whenever no end was crossed. The qualifier is load-bearing. Under wrap=false the pair is genuinely not reversible at the ends, because the first press was absorbed and the second one moves; under wrap=true it is not reversible across the seam for the same reason in reverse. Asserting reversibility without the qualifier fails on a correct implementation, which is how the qualifier usually gets deleted instead of the bug.

4. Typeahead is a search, not a move — and it has its own edges

Type b in a menu and you expect to land on the next item starting with b. Type it again and you expect the one after that, cycling. Type b then o and you expect “Bo…”, not the next item starting with o. So the buffer decides the needle: all the same letter means cycle on that letter, anything else means match this prefix, starting from where you already are.

Two consequences worth stating rather than discovering. Typeahead skips disabled items like every other move — a search that lands you somewhere you cannot act is worse than a search that finds nothing. And typeahead wraps even when the arrows do not: clamping is a statement about a direction, and a search does not have one. The buffer resets on any navigation key and on an explicit timeout event, which the engine takes as an input rather than reading a clock — a state machine that reads the clock cannot be walked exhaustively.

5. aria-activedescendant is the other answer, not the wrong one

There is a second way to make a composite widget one tab stop: focus stays on the container forever and aria-activedescendant names the item that is currently active. It ties roving on the headline number. The difference is where focus actually is.

🔴 Same tab-stop count, opposite mechanism. With roving, the item is really focused — :focus and :focus-visible style it for free and document.activeElement is the thing the user is on. With activedescendant the item is never focused, so you draw the active ring yourself, and document.activeElement is the container: the element the browser thinks is focused and the element the user is on are two different elements, permanently. What that buys is items that never need to be focusable at all, which is why virtualised listboxes and comboboxes reach for it — a combobox cannot move DOM focus into its list without taking it out of the input the user is typing in.

What this models and what it does not

The engine is the keyboard state machine and nothing else: an item list, an active index, wrap, orientation, a typeahead buffer, and reduce(state, key). The configurations are enumerated rather than sampled, so there is no generator and no seed, and the counts are exact rather than estimated. Out of scope, each of which is real work in a real widget: applying the resulting tabindex to elements and calling .focus(); items added or removed while the widget is focused, where the active index has to be re-derived and can go stale; RTL, which swaps what ArrowLeft means; two-dimensional grids, where Home/End have both a row meaning and a grid meaning; and Page Up / Page Down. The keystroke figures are counts of engine transitions, not timings — nothing on this page was measured in a browser.

How it works

// the whole pattern, in two lines
const tabIndexOf = (state, i) => (i === state.activeIndex ? 0 : -1);
const next = (items, from, dir, wrap) => /* first ENABLED index that way */;

// and the whole correctness story, in one
items.filter((_, i) => tabIndexOf(state, i) === 0).length === 1

The engine holds no DOM and no clock. Buffer expiry arrives as a Timeout key rather than a setTimeout, so the machine is a pure function of the keys pressed and every reachable state can be enumerated. The demo that puts real tabindex attributes on real buttons lives outside the engine block, where it belongs.
