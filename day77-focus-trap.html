DESIGNFROMZERO · DAY 77

▣ Focus trap — the loop that keeps Tab inside an open dialog. There is one thing every focus-trap test asserts: Tab never leaves the dialog, Tab from the last control wraps to the first, Shift+Tab from the first wraps to the last. On a suite of eight fixtures written the way fixtures are really written, all of that holds for seven of these eight traps — and six of the seven are wrong. It cannot be otherwise: the same assertions pass for 3,600 of 3,600 lists drawn at random from the dialog in random order, because a cycle is a cycle whatever is in it. Meanwhile the trap in the most shipped code sends the keyboard to somewhere the reader cannot see on 1,184 of 1,500 generated dialogs — 16.4% of every Tab press, and six presses in a row on the worst of them with the focus ring never moving — while 1,132 of those dialogs hold a control that no amount of Tab can reach at all. Five more fixtures, sixteen extra elements of markup, take the suite from accepting seven to accepting one. 1,583,935 assertions on load. Pure vanilla JavaScript, one file, no build step.

Click the dialog below and press Tab. Nothing inside it is a real form control — the demo draws the dialog from the same tree the engine reads, so the ring you see is the one the chosen trap computed and not the browser's own focus. Rows with a hatched border are in the markup but not on the screen: behind a display:none panel, inside a closed <details>, painted out by visibility:hidden, or under an inert ancestor. When the ring lands on one of those, you have pressed Tab and nothing has happened.

WHAT DID NOT SURVIVE THE MEASUREMENT

The two lines everyone writes, and the list they run on

A modal dialog has to hold the keyboard. Open it, and Tab must walk the controls inside it and then come back to the top instead of wandering off into the page behind. Every implementation of that is the same six lines: collect the focusable elements, find where focus is now, and if the next step would fall off either end, put it back on the other end.

The wrap is not where the bugs are. The wrap is four lines of modular arithmetic and it is right in almost everything shipped. The bug is in the word collect.

What a tab stop actually is

The platform's rule has four parts and only the first one is on the element itself.

  • Is it rendered? Not if it or an ancestor is display:none, not if it carries the hidden attribute, and not if it is inside a <details> that is closed — a closed details renders only its first <summary>.
  • Is it painted? visibility inherits, so an element with no visibility of its own is hidden if an ancestor is — and a descendant can set visibility:visible and come back. A check that stops at the element, or one that stops at the first hidden ancestor, gets a different answer than the cascade does.
  • Is it switched off? disabled is an attribute on four elements, and a <fieldset disabled> carries it down to every control inside. inert does the same for everything, and neither leaves an attribute on the element you are testing.
  • Does it want the keyboard? tabindex, parsed as an integer. Negative means focusable but not in the tab order. Zero means in the order, in document position. Positive means in the order before all the zeros, sorted by value.

Three of those four inherit. The selector string everyone starts from tests none of them.

Two details that look like pedantry and are not

[tabindex="-1"] is an exact string compare. HTML parses the attribute with the rules for parsing integers: leading whitespace is skipped, a sign is allowed, digits are collected, and trailing rubbish is ignored. So tabindex=" -1" and tabindex="-01" are both minus one to the platform and neither one matches the selector. They come straight through into the list.

A radio group is one tab stop, not one per button — but only while one of its buttons is checked. Nothing checked and every button is a stop, because you have to be able to get to the group at all. A trap that treats radios as ordinary inputs hands the keyboard three stops where the platform gives one, and the two lists differ by exactly the number of buttons in the group minus one.

Why a test cannot tell you any of this

Write the fixture. Three buttons in a dialog, or a field and two buttons: it has to be something you can type and read. Now assert the things you can assert — focus stayed inside, the last one wrapped to the first, the first wrapped back to the last, a full lap came home.

Every one of those is a statement about a cycle. The stepping rule turns any list into a cycle, and a cycle drawn from the dialog stays in the dialog. So the assertions hold for the correct list, for a list missing half the controls, for a list with three invisible elements in it, and for the same list shuffled — which the page above demonstrates by drawing thousands of lists at random and finding no exceptions. The one arm that fails is the one with no trap installed at all, and it fails because its list is not drawn from the dialog.

The fixture is the blind spot, not the assertion. A fixture with one display:none panel in it — four extra lines — rejects the selector string immediately. Five such fixtures reject everything except the platform's own rule.

The sentinel

There is a second implementation shape worth naming, because it is the best of the wrong ones. Instead of intercepting keydown, put two focusable elements of zero size at the top and bottom of the dialog; tabbing off the end reaches one, and its focus handler sends focus to the element it cached as first. It is a good trick: it gets the whole middle of the order right for free, because the browser is doing the walking.

It caches those two ends from a document-order query. Put one tabindex="1" anywhere in the dialog and the tab order no longer starts where the markup starts, so both ends now point at the wrong control — and only at the ends, which is exactly where a test that walks the middle never looks.

What to do instead

  1. Do not write the selector. inert on everything outside the dialog is one attribute and the platform computes the whole list for you.
  2. If you must compute the list, compute the four questions above, and compute the inherited three by walking the ancestors rather than reading the element.
  3. Parse tabindex as a number. Never string-compare it.
  4. Sort. Positive values first, ascending, then everything else in document order.
  5. Collapse checked radio groups.
  6. Add the five fixtures. They are sixteen extra elements between them, and they turn a suite that accepts almost anything into one that accepts almost nothing.

How this page was built

Nine steps. Everything between ENGINE:BEGIN and ENGINE:END in this file is a pure function of a tree of plain objects: no DOM, no clock, no Math.random. The demo draws that tree; it never reads what it drew.

1. Make the dialog data

A node is { tag, k, ...attributes } and a missing field means the attribute is absent, which is never the same as present-and-false. That distinction is the whole subject: disabled absent, disabled="" and disabled="false" are all the same to HTML and all different to a naive check. 

function N(tag, o, kids){
  const n = { tag: tag, k: kids || [] };
  if (o) for (const key in o) n[key] = o[key];
  return n;
}

2. Resolve the inherited things once

Rendering, visibility, inertness and fieldset disabling all inherit. One preorder walk resolves all four and stamps the answer on the node, so nothing downstream ever climbs back up the tree — and the naive reading of visibility is computed in the same walk, as a separate field, so the two can be compared rather than argued about.

3. Write the platform's rule

Rendered, painted, not inert, not disabled, then tabindex parsed as an integer: negative is out, zero or positive is in, absent falls back to whether the element is focusable by nature. Then collapse checked radio groups. Then sort.

4. Write the seven others as one added clause each

Each trap is the same stepping rule over a different list. That is the point of the arrangement: the traps cannot differ for a reason nobody named, because the only thing that differs is one clause.

5. Decide correctness, do not sample it

Two traps agree when they send the keyboard to the same place from every position it could be in, in both directions, including from nowhere. The domain is the nodes of the dialog plus null, which is finite, so the comparison is exhaustive. 

for (const fid of universe){
  if (a(fid,  1) !== b(fid,  1)) return false;
  if (a(fid, -1) !== b(fid, -1)) return false;
}

6. Keep the empty dialog

Some dialogs have no tab stop at all — a confirmation whose close button is disabled. The right answer is that there is nowhere to go, and next() returns null. Every assertion a test can make is then vacuously true, which is worth knowing: a suite containing only that fixture accepts all eight arms including the control.

7. Prove the assertions are blind, do not assert it

Draw lists at random out of the dialog, in random order, including nodes that are not tab stops. Run the same five assertions. They all pass, every time, which is what makes the headline a fact about the assertions rather than a complaint about six libraries.

8. Predict each defect from the markup

For each neighbouring pair of traps, write the predicate that says whether they can differ on this dialog — read off the tree, with no implementation in it — and then check it against whether they really did. Two of those predicates are exact counts rather than booleans: the number of invisible stops the selector string produces, and the number of extra stops a checked radio group costs.

9. Print the nulls

Three things did not survive: the fix everybody reaches for buys almost nothing and makes one thing worse, one of the five new fixtures turns out to be redundant, and one of the five assertions cannot fail on a fixture at all. They are on the page above rather than in a drawer.
