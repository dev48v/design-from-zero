A diff is a shortest path, not a comparison


      
Lay the old file down one axis and the new file down the other. You start at the top-left
      corner and must reach the bottom-right. Moving right consumes a line of the old file — that is
      a deletion. Moving down consumes a line of the new file — an
      insertion. And wherever the two lines match you may move diagonally
      for free.


      
The best diff is the cheapest path across that grid, and because diagonal moves are free
      the cost of a path is exactly its number of edits. So "what changed" is a shortest-path
      question, and the answer is not a matter of taste.


      
1. Myers: search by edit count, not by position


      
The trick in Myers' algorithm is what it iterates over. Instead of filling an
      n×m table it asks, in order: can I get there in 0 edits? in 1? in
      2? — and for each budget d it only records, per diagonal, the furthest point
      reachable. The first budget that reaches the corner is the minimum, and there is nothing to
      verify afterwards.


      
for (let d = 0; d <= N + M; d++){
  for (let k = -d; k <= d; k += 2){          // k = x - y, the diagonal
    let x = (k === -d || (k !== d && v[k-1] < v[k+1])) ? v[k+1] : v[k-1] + 1;
    let y = x - k;
    while (x < N && y < M && a[x] === b[y]) { x++; y++; }   // the snake: free moves
    v[k] = x;
    if (x >= N && y >= M) return backtrack(trace, d);        // first arrival = minimum
  }
}


      
That inner while — the "snake" — is where all the work happens: it runs the
      free diagonal as far as it goes. The cost is O((N+M)·D) in the number of
      edits D, which is why a real diff of a 4,000-line file with a three-line change is
      instant while a full LCS table would be sixteen million cells.


      

        
Minimality here is structural. It is not asserted, not
        checked, not approximated — it is a consequence of visiting edit counts in increasing order.
        Which is exactly why a subtly rearranged version of this loop still returns a valid
        edit script, and nothing downstream notices.

      


      
2. The property everybody tests, and what it misses


      
Every diff test in the world is some version of this:


      
assert(applyPatch(oldFile, diff(oldFile, newFile)) === newFile);


      
It is a real property and it catches real bugs. It is also satisfied by this:


      
function diff(a, b){
  return [...a.map(deleteLine), ...b.map(insertLine)];   // "everything changed"
}


      
Delete every line, then insert every line. The patch is valid. It applies on the first try.
      It round-trips on 100% of the 6,000 pairs measured on the first tab, and it
      shows a reviewer 10.9× as many changed lines as the correct answer. A
      diff has two jobs — reconstruct the file and be short — and the test suite
      almost always covers only the first.


      
So the second job needs an oracle, and it has to come from somewhere the diff cannot reach.


      
3. An oracle that costs nothing


      
The obvious oracle is the LCS table: minEdits = n + m - 2·LCS(a,b). It
      is correct and it is O(n·m), which puts a hard ceiling on how much fuzzing
      you can afford.


      
But there is a family of inputs where the answer is a closed form. Take a
      file in which every line is distinct. Delete some of its lines, and insert some brand-new
      lines that appear nowhere else. Now the only lines the two files share are the survivors, and
      because nothing repeats, those survivors are the longest common subsequence — they cannot be
      matched in any other way. So:


      
LCS(a, b) = |a| - deletions
minEdits  = (|a| - LCS) + (|b| - LCS) = deletions + insertions


      
The generator knows how many of each it made, so the minimum is known before the diff runs,
      in O(1). That is what makes 6,000 pairs of 12–52 lines affordable — and the
      slow LCS table stays for the cases the closed form genuinely cannot reach.


      
4. And the closed-form class is the easy one


      
This turned out to be the sharpest measurement on the page, and it was not the intent.
      Two of the wrong algorithms — scan ahead for the next matching line and
      unique-line anchors — score a flat 0.0% on 6,000 distinct-line
      pairs. Perfect. Then the same code, the same oracle logic, run on source files where lines
      repeat:


      
                      distinct lines      source code
scan ahead                    0.0%            37.1%
unique-line anchors           0.0%            42.6%


      
The mechanism is visible in the smallest failing case. Anchors are lines that occur exactly
      once in both files. Delete a function header and it is no longer unique on both sides,
      so it stops being an anchor, and the whole region that used to be pinned by it falls back to
      the crude path — eight edits for a two-line deletion. A test corpus of files with no repeated
      lines cannot find that, and a test corpus of files with no repeated lines is exactly what a
      generated fixture looks like.


      
5. Below the minimum is a different kind of wrong


      
Comparing 32-bit hashes instead of strings is a standard optimisation, and it is correct
      only if a matching hash is treated as a candidate and confirmed. Skip the
      confirmation and two different lines become the same line. Here is the whole failure in one
      edit:


      
-   const total = a + b;
+   const total = b + a;


      
A checksum that adds character codes cannot tell those apart — they are a perfect anagram.
      The hash diff reports zero changes, the viewer shows an unmodified file, and
      applying the patch gives you back the old version. Round-trip catches this one, on
      16.1% of source-code pairs.


      
But there is a cheaper signal, and it needs no expected output at all: this diff reported
      fewer edits than the proven minimum. No correct diff can ever do that. An
      edit count below the minimum is not a quality problem, it is a proof that the equality test is
      lying.


      
6. Hunks: the second algorithm on the page


      
Nobody wants the whole file. A diff viewer shows each change with context
      lines around it, and merges two changes into one hunk when they are close enough to run
      together. "Close enough" has exactly one correct threshold:


      
split the hunks  <=>  gap > 2 * context


      
Because if the gap is exactly 2·context, the trailing context
      of the first hunk and the leading context of the second meet perfectly — they cover the gap
      with nothing left over and nothing counted twice. Writing >= instead of
      > splits at that boundary, and the result is:


      
gap = 6, context = 3

  correct : @@ -2,14 +2,14 @@          one hunk
  off-by-1: @@ -2,7 +2,7 @@            two hunks
            @@ -9,7 +9,7 @@

  lines rendered: IDENTICAL, in the same order, each exactly once


      
Over 4,000 documents that off-by-one changes the hunk count on 29.7% of
      them and the rendered output on none. Every assertion about what appears on
      screen passes. The only thing that differs is a header count.


      
Move the boundary one step further — split whenever the gap exceeds one
      context — and it becomes loud: the two contexts now overlap and the same lines print
      twice, 5,975 times across the same 4,000 documents. One off-by-one is invisible and its
      neighbour is obvious.


      

        
Except at the boundary itself, which is where this page was first
        wrong. At a gap of exactly 2·context the greedy rule splits too, and
        its two hunks land adjacent — no overlap, no duplication, the same page again.
        The loud bug is only loud in the narrow band where the gap is wider than one context and
        narrower than two. A fixture built at the interesting boundary for one bug turned out to be
        the worst possible fixture for the other, and the assertion written against it failed.

      


      
What is deliberately left out


      
Move detection is a different problem — a block that travelled from the top of the file to
      the bottom is minimal as a delete plus an insert, and showing it as a move means
      leaving the shortest-path formulation behind. Real diff tools cap the search
      (D can reach N+M on files with nothing in common) and fall back to
      the trim-and-replace path on the way out, which is why a legitimate tool sometimes emits the
      null diff of this page on purpose. Line-ending normalisation and tab expansion happen before
      any of this and change what "equal" means. And a three-way merge needs the common ancestor,
      not two files, so none of the above applies to it directly.


    

  






  

    


      
🔨 How it is built


      
1. Six pure functions and no DOM

      
myersOps(a, b)              -> [{t:'eq'|'del'|'ins', ai, bi, text}]
applyOps(a, ops)            -> string[]        // the patch, applied
editCount(ops)              -> number
wellFormed(ops, n, m)       -> { bad, checks }
groupHunks(ops, ctx, rule)  -> [{from, to}]    // op-index ranges
wordDiff(x, y)              -> ops, over tokens instead of lines

      
The op list carries indices, not text, except on insertions — which carry the
      literal line the way a real patch file does, so applyOps needs only the old file.
      Everything above the renderer is pure, which is what makes ten thousand pairs a load-time
      check rather than a build step.


      
2. Word-level highlighting is the same function again

      
const tokenize = s => s.match(/\s+|[A-Za-z0-9_]+|[^\sA-Za-z0-9_]/g) || [];
const wordDiff = (x, y) => myersOps(tokenize(x), tokenize(y));

      
Nothing new is needed. A line diff is Myers over an array of strings; an intra-line diff is
      Myers over an array of tokens. Keeping whitespace as its own token is what stops
      foo(a,b) and foo(a, b) highlighting as a total rewrite.


      
3. The structural check nobody writes

      
// indices must march forward exactly one at a time on each side,
// and finish at the end of BOTH files
let ai = 0, bi = 0;
for (const op of ops){
  if (op.t === 'eq')  { assert(op.ai === ai++); assert(op.bi === bi++); }
  if (op.t === 'del') { assert(op.ai === ai++); }
  if (op.t === 'ins') { assert(op.bi === bi++); }
}
assert(ai === a.length && bi === b.length);

      
Round-trip already implies most of this, but not all of it: a diff can reconstruct the file
      while pairing an eq op against the wrong line on one side. Splitting the two
      checks is what lets the fuzz table say which kind of wrong each variant is.


      
4. Two oracles, priced differently on purpose

      
// (a) CLOSED FORM - O(1). Only valid when no line repeats and every inserted
//     line is brand new, which the generator guarantees by construction.
minEdits === deletions + insertions

// (b) FULL LCS TABLE - O(n*m). Correct on anything, and the reason the
//     source-code pass is capped at short files.
function dpMinEdits(a, b){
  let prev = new Int32Array(m+1), cur = new Int32Array(m+1);
  for (let i = 1; i <= n; i++){
    for (let j = 1; j <= m; j++)
      cur[j] = a[i-1] === b[j-1] ? prev[j-1] + 1
                                 : Math.max(prev[j], cur[j-1]);
    [prev, cur] = [cur, prev];
  }
  return n + m - 2 * prev[m];
}

      
Oracle (a) does 6,000 pairs of up to 52 lines for free. Oracle (b) does 4,000 pairs of
      about 20 lines for two million table cells. Same question, two thousand times the price — and
      the expensive one is the only one that can see the two heuristics fail, which is the whole
      argument for keeping both.


      
5. What the tests pin

      
// the correct core is minimal on every pair, under BOTH oracles
assert(editCount(myersOps(a,b)) === dels + inss);       // closed form
assert(editCount(myersOps(a,b)) === dpMinEdits(a,b));   // LCS table

// no diff may ever report fewer edits than the minimum
assert(stats.every(s => s.belowMinimum === 0 || s.key === 'weakhash'));

// and the broken ones really are broken - on the same inputs
assert(nuke.applyFail === 0);           // <- the point of the whole page
assert(nuke.aboveMinimum === trials);
assert(scan.aboveMinimum === 0);        // on distinct lines
assert(scan.aboveMinimumOnCode > 0);    // on files that repeat themselves

// the grouping off-by-one is invisible in the rendered output
assert(ge.rendersIdenticallyToCorrect === documents);
assert(ge.hunkCount !== correct.hunkCount);


      
6. The assertion that matters most is the first broken one

      
Asserting that the null diff passes round-trip is the load-bearing test on
      this page. If it ever starts failing, the harness has drifted, not the bug — and the reason to
      measure edit counts, extra edits and rendered-line multisets at all is that the obvious
      assertion is provably unable to separate the best possible answer from the worst one.
