DESIGNFROMZERO · DAY 73

▶▶ Toolbar overflow — the row of controls that does not fit, and the +3 chip standing in for the ones that came off it. There is exactly one number to compute, how many controls come off, and the space you must set aside for the chip is a function of that number, so the fit test is self-referential and no single forward pass over the row can be right. That is the part everyone gets wrong, and it is not the interesting part. The interesting part is that overflow — the only thing you can see, and the only thing anybody tests — is satisfied at every one of 2,309 whole-pixel container widths by five of these eight implementations, and three of those five are wrong: one permanently gives up a control that fits, on 10.3% of widths; one hides the wrong controls on 78.5% of them while its count is right on 47.7%; and one is right on all five properties at every single width and never stops repainting — 688 of 759 widths are a two-cycle, because it measures the row it just changed. Also here: the 3 pixels of container width where hiding one control makes the row wider than showing everything, which is the chip minus the control it stands in for and nothing else — an identity with 0 violations in 3,600 checks, and the reason a bisection is not entitled to an answer. 6,461,761 assertions on load. Pure vanilla JavaScript, one file, no build step.

🧠 What is actually going on

      

        A toolbar is a row of controls in a container that is sometimes narrower than the row. When
        that happens some controls have to come off and go into a menu, and something has to be on
        the row to open that menu — a ··· button, or a
        +3 chip that says how many went away. The pattern has a name, priority
        plus, and the whole component is one integer: how many controls come off.
      

      

        It looks like the easiest layout problem there is. Add up the widths until you run out of
        room. It is not, and the reason is one sentence long.
      


      
1. The space you must reserve is a function of the answer

      

        The chip is a box on the row, so it costs width, so you have to leave room for it before you
        decide how many controls fit. But its label is +3, and 3 is the
        number you are trying to compute — and +3 and +12 are not the
        same width, because a digit is about seven pixels. The reserve depends on the answer and the
        answer depends on the reserve.
      

      

        This is why the loop everybody writes cannot be right. It walks the controls, keeps a running
        total, subtracts some constant for the chip, and stops. Whatever constant it picks is wrong
        somewhere: pick the width of +1 and the row overflows as soon as ten controls are
        hidden; pick the width of +14 and you permanently hold back seven pixels you did
        not need, which on a real toolbar means one whole button that fitted.
      

      

        The way out is to stop trying to compute it forwards. There are only n + 1
        possible answers — hide none of them, hide one, hide two, up to hide all of them —
        and each one has a width you can evaluate exactly, chip and all, because at that point you
        know how many are hidden. So you do not compute the answer, you check the
        candidates and take the smallest one that fits. That is the entire correct
        implementation, and it is shorter than the loop it replaces.
      


      
2. Count the boxes, not the controls

      

        The row's width is the sum of the visible controls, plus the chip if there is one, plus one
        gap between every pair of neighbours. The number of gaps is boxes minus one, and the
        chip is a box. Write gap × (shown − 1) instead of
        gap × shown when the chip is present and you are exactly one gap short: on
        the sweep in the first tab that is an eight-pixel overflow on
        9.9% of container widths, never more and never less than
        8px. Eight pixels is not enough to see and is more than enough
        to push a rounded corner under the edge of a panel.
      

      

        Leaving the chip out of the budget altogether is the loud version of the same mistake:
        1,232 of 2,309 widths overflow, by up to
        50px, which is a whole control hanging outside the container.
        That one gets caught the first time anyone looks at the page. The eight-pixel one does not.
      


      
3. Which controls, not just how many

      

        The count is half the component. The other half is which controls come off, and the
        answer is not “the ones on the right”. A document toolbar's least important
        control is the checklist toggle, which sits in the middle; a mail toolbar's is
        Add task. Priority is a product decision that has nothing to do with source order,
        and it is stored as a number on each control.
      

      

        Hiding right-to-left instead is the single most common implementation of this component, and
        on the real toolbars in the first tab it produces the smallest count that fits on
        47.7% of widths and the correct set of controls on
        21.5% of them — while never once overflowing the
        container. There is no packing property that can see it, because it is not a packing error:
        the count is often exactly right and the controls are the wrong ones. On the one generated
        corpus that can see it at all — random widths with priority shuffled — its count
        is right on 43.8% of widths and its set on
        5.3%.
      


      
4. Hiding one thing can make the row wider

      

        Every step of “hide one more” removes a control and removes the gap that was next
        to it. Every step except the first, because going from nothing hidden to one
        thing hidden swaps a control for a chip and leaves the number of boxes on the row exactly
        the same. So that one step has no gap to pay with, and if the chip is wider than the control
        it stands in for, the row gets wider.
      

      

        The size of the effect is an identity, not an estimate: the window of container widths in
        which everything fits but hiding one thing does not is
        chip(1) − width of the least important control pixels wide, clamped at
        zero. That is checked against 3,600 generated
        toolbar-and-chip pairs on load, with 0 violations and zero
        cases of the row getting wider at any other step.
      

      

        On the mail toolbar with a +N chip that window is three pixels wide, which sounds
        like nothing until you notice what it does to the search. The hidden counts that fit are
        not a contiguous run any more — nought fits, one does not, two does — and
        a binary search over a predicate with a hole in it returns whichever side it happened to land
        on. In those three pixels it hides two controls where nought
        was correct. Bisecting the hidden count is a real optimisation, because each candidate you
        evaluate can cost a forced reflow, and it is exactly right
        100.0% of the time with a round
        ··· button and 99.7% with a
        +N chip.
      

      

        Which is the sentence worth taking away: whether your overflow control shows a count is a copy
        decision, and it decides whether the layout problem underneath it is monotone.
      


      
5. Where the widths come from is not a detail

      

        Every number above assumes you know how wide each control is. Getting those numbers is the
        part that goes wrong in production, because the obvious way is to measure the DOM —
        ResizeObserver fires, you read getBoundingClientRect on each
        control, you re-fit.
      

      

        A hidden control is display:none and measures zero. So the pass that runs after
        you hide three controls adds up the widths of the ones that are left, concludes that the row
        has become small enough to show everything, un-hides them, measures again, finds the row too
        wide, and hides them again. The arithmetic was never wrong. On the document toolbar
        688 of 759 container
        widths have no fixed point at all under that rule, and the ones that do are the ones
        where the container is too narrow to show anything either way.
      

      

        The fix is not in the fitting pass. Measure the controls once from a layout where they are all
        visible — a copy of the row kept off-screen, or a single measurement pass before the
        first hide — and cache the widths against the font and the text, not against the current
        state of the row.
      


      
6. Priority is not the packing optimum, on purpose

      

        If you wanted to fit as many controls as possible you would drop the widest ones first, and on
        the project board toolbar that shows +32.1% more controls than
        the priority rule does. The subsets that win are the ones that throw away the search field and
        the primary button to keep three icons. A toolbar that does that is worse in every way that
        matters and better on the only metric someone thought to measure, which is a good description
        of most layout bugs.
      


      
7. What the fixture cannot see, and why that is computable

      

        The corpus almost every test of this component runs on is four to six identical text buttons
        with priority left to right. Two of the seven defects on this page are not unlikely on that
        corpus, they are impossible, and both reasons are arithmetic:
      

      
    
        
  • 
          digits(1) and digits(n) are the same number for every
          n below ten, so on a toolbar with fewer than ten controls the one-digit reserve
          and the widest reserve are the same function — identical on
          41,122 of 41,122 container widths, and different on
          8.0% of the widths of toolbars that have ten or more.
        
    • 
        
  • 
          When priority runs left to right, “give up the last controls” and “give up
          the least important controls” are the same instruction — identical on
          102,592 of 102,592 widths with random widths
          throughout. So the blindness is not about the widths at all. It is about the priority
          order, and a fixture author has no reason to shuffle it.
        
    • 
      

      

        Which means you can work out in advance which defects a corpus is capable of finding, and that
        is a more useful thing to know about a corpus than whether it looks like production.
      


      
8. Five properties and what each one is worth

      

        The row stays inside the container is the one everybody writes, and over-hiding never
        overflows, so it is satisfied by five of the eight
        implementations at every width. The chip appears exactly when something is behind it
        is 100.0% for all eight, because every one of them derives the chip from its
        own answer; it is a property of the render, not of the fit. Widening the window never
        takes a control away is 0 violations for all eight, for a
        structural reason: each pass minimises over candidates whose widths do not depend on the
        container, so widening it can only add candidates.
      

      

        You could not bring one more control back is the cheap version of the real property
        and it is nearly as strong — it is what you would write if you did not want to
        reimplement the fit inside the test. And it hid the smallest count that fits, and it hid
        the controls the product chose is the specification. It is the only column that separates
        the safe-looking mistakes from the correct answer, and it is the only one nobody writes,
        because writing it means writing the implementation twice.
      

    

  






  

    

      
🔨 How it is built


      
1. One block of pure functions and no DOM

      

        Everything between ENGINE:BEGIN and ENGINE:END is arithmetic over
        numbers. The three chip shapes are TRIGGERS; the toolbars are
        TOOLBARS plus three generators; the eight fitting passes are IMPLS,
        each a single fit(P, W, gap, trig); the studies are sweep,
        realSweep, corpusSweep, holeAt,
        feasibleShape, holeIdentity, reserveTwins,
        domTwins, widenStudy, flickerStudy and
        priceOfPriority. The verifier lifts that block out of the page with a regular
        expression, refuses it if it so much as mentions document, and runs it under node
        against oracles written separately from it.
      


      
2. Prefix sums over the order things are given up in

      

        prep() runs once per toolbar and fixes two things. The first is the order controls
        are surrendered in — least important first, and among equals the rightmost first,
        because that is the one the eye misses. The second is the running total of the widths given up
        along that order, so rowWidth(P, h, gap, trig) is a subtraction and two
        multiplications rather than a loop. A whole-pixel sweep over a thousand container widths times
        eight implementations times five properties is only affordable because the width of a
        candidate is O(1).
      


      
3. Two representations of the same width

      

        rowWidth is the closed form: total, minus what is hidden, plus the chip, plus
        gap × (boxes − 1). placeWidth is the other one: walk the
        controls, skip the hidden ones, advance a cursor by a gap and a width for each, and read the
        right edge. No prefix sums, no formula, and it is what the browser does. Every property check
        in the sweep goes through placeWidth, and every toolbar additionally has all
        n + 1 of its candidate widths checked both ways. The page prints that agreement
        count under the live table.
      

      

        The demo adds a third: after the row is laid out it reads the real
        getBoundingClientRect of the first and last boxes and prints the difference next
        to the modelled number. The boxes carry explicit pixel widths and the row is a flex row with
        an integer gap, so the two are the same integer and the page says so on every
        repaint.
      


      
4. Eight passes, one clause apart

      

        Every implementation answers the same question with the same signature, and the difference is
        named in its note. Four of them differ only in what they reserve for the chip
        (the right amount, the widest, one digit, nothing at all, or the right amount but one gap
        short). One differs only in how it searches the candidates (bisection instead of a scan). One
        differs only in which controls it gives up (right to left instead of by priority). One differs
        only in where the widths come from. Keeping them all one clause apart is what makes the
        property tables mean anything — each column change is attributable to one line.
      


      
5. A whole-pixel sweep, not a sample

      

        Container width is an integer number of pixels, and the useful range is a few hundred of them,
        so there is no reason to sample: sweep walks every whole pixel from the narrowest
        width the chip alone fits in up to a width that holds the entire row, and the percentages on
        this page are counts of pixels. That is why a three-pixel window shows up at all, and why the
        numbers do not move between reloads.
      


      
6. The re-measuring pass as a dynamical system

      

        liveStep(P, W, gap, trig, hCur) is the implementation that reads the DOM,
        expressed as a map from the current hidden count to the next one: hidden controls contribute
        zero to the measured total, everything else is the same arithmetic.
        liveOrbit then iterates it from a fully expanded row, keeping a
        Map of the states it has seen, and classifies the orbit as a fixed point, a
        two-cycle or something longer. That is the only honest way to ask whether a toolbar settles,
        because a single call to this implementation is exactly correct — the defect
        does not exist in one pass, only in the sequence.
      


      
7. Exhaustive subsets, deliberately

      

        priceOfPriority enumerates all 2^n subsets of the row and keeps the
        largest that fits. At fourteen controls that is 16,384 subsets per container width, so it runs
        on a stride rather than every pixel, and it is the one study on the page that is a sample. It
        earns its cost by answering a question none of the fitting passes can: not did this
        implementation do what it was told but what was the most this row could ever have
        carried.
      


      
8. What the verifier does differently

      

        It shares no line with the engine. Row widths are recomputed as integer
        placement over a rebuilt item list; the giving-up order is rebuilt by a
        counting argument over priorities rather than a comparator sort; the smallest
        feasible count is found by building the whole feasibility bitmask and reading
        its lowest set bit; the hole identity is re-derived from the chip and the item widths with no
        sweep at all; and the price of priority is recomputed by a
        dynamic program over widths instead of subset enumeration, which is a
        completely different algorithm that has to produce the same integer. Every percentage the page
        prints is recomputed from the same seeds through those oracles rather than restated.
