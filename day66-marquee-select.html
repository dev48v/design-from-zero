DESIGNFROMZERO · DAY 66

🔲 Marquee select — drag a box over a canvas of items and select what it touches. Four lines of geometry, and every one of the four is a place people get it wrong. The band is defined by the anchor and the current pointer, not by where the pointer has been — track the path and dragging up-and-left selects nothing. Hit testing is AABB overlap, not containment, and the correct test is the negation of four disjointness checks rather than four positive ones. Modifier keys make the operation set algebra over a snapshot of the selection taken at drag start — recompute from the live selection and shift-drag toggles items on and off as you wiggle. And the coordinates must be content space, not viewport space: the moment the container scrolls mid-drag, a band stored in client coordinates detaches from the items it is drawn over. All four are fuzzed here against an independently written checker over 40,000 random drags, and the page reports where each naive version breaks. Pure vanilla JavaScript, one file, offline.

Drag on the empty background to draw a band. Hold Shift to add, Alt to subtract, Ctrl to toggle. The canvas scrolls — scroll it mid-drag and watch the band stay attached to the content.

Four lines of geometry, four ways to get it wrong


      
1. The band is anchor-to-pointer, not a path


      
The instinct is to grow a rectangle as the pointer moves. The correct model is simpler and
      stateless: store the anchor once at pointerdown, and every frame the band is
      the rectangle spanned by the anchor and the current point.


      
const band = {
  x: Math.min(anchor.x, p.x),  y: Math.min(anchor.y, p.y),
  w: Math.abs(p.x - anchor.x), h: Math.abs(p.y - anchor.y)
};


      
Those Math.min calls are the normalisation, and without them a drag up and to
      the left produces negative width and selects nothing — the classic symptom, and it looks like
      the feature "only works one way".


      
2. Overlap, not containment


      
An item is selected if the band touches it. Almost nobody wants containment — you
      would have to enclose every icon entirely, which on a dense canvas means dragging past the
      edges of the viewport.


      
And the overlap test is best written as a negation:


      
const overlaps = (a, b) => !(a.x + a.w < b.x || b.x + b.w < a.x ||
                            a.y + a.h < b.y || b.y + b.h < a.y);


      
Four disjointness checks, all of which must fail. The positive version needs eight
      comparisons and a case analysis, and the case analysis is where the bugs live. Turn on
      containment on the page and watch the selection collapse.


      
3. Modifiers are set algebra over a snapshot


      
Shift adds, Alt subtracts, Ctrl toggles. The subtlety is what they operate on:


      
// captured ONCE, at pointerdown
const base = new Set(selection);

// every frame
const hit = itemsIn(band);
next = shift ? union(base, hit)
     : alt   ? difference(base, hit)
     : ctrl  ? symmetricDifference(base, hit)
     : hit;


      
Recompute base from the live selection each frame and Ctrl-drag becomes
      unusable — every frame toggles the same items again, so they flicker on and off as your hand
      shakes. The snapshot makes the whole gesture a pure function of (base, band), which is also
      what makes it testable with no DOM.


      
4. Content coordinates, not viewport coordinates


      

        
This is the one that survives review and breaks in use. Store the anchor
        in client coordinates and everything works — until the container scrolls during the drag.
        Then the anchor refers to a point on the screen while the items live in the
        content, and the band detaches from what it is drawn over.

      


      
const toContent = (e) => ({
  x: e.clientX - rect.left + el.scrollLeft,
  y: e.clientY - rect.top  + el.scrollTop
});


      
Two additions. Toggle the viewport-coordinate checkbox on the page, scroll mid-drag, and
      the failure is immediate and obvious — which is exactly why it never shows up in a demo where
      nothing scrolls.


      
The thing that makes all of this testable


      
None of the four functions touch the DOM. normaliseBand,
      overlaps, itemsIn and applyModifier take numbers and
      return numbers, so 40,000 random drags run in milliseconds under node with no browser at
      all — and the naive variants can be run side by side on the identical drags rather than
      argued about.


      
What is deliberately left out


      
Auto-scroll when the pointer leaves the container is a real feature and it is not here: it
      needs a timer, and a timer makes the gesture stateful again, which would cost the property
      that makes the rest testable. Rotated items would need SAT rather than AABB. Both are worth
      knowing you have skipped rather than discovering later.


    

  






  

    


      
🔨 How it is built


      
1. Everything is a pure function

      
normaliseBand(anchor, point)        -> {x, y, w, h}
overlaps(a, b)                      -> boolean
itemsIn(band, items, mode)          -> Set<id>
applyModifier(base, hit, modifier)  -> Set<id>

      
No element, no event, no state. The DOM layer converts a pointer event into a content-space
      point and calls these; everything else is arithmetic, which is what makes the fuzz possible.


      
2. The overlap test, and why it is a negation

      
const overlaps = (a, b) => !(a.x + a.w < b.x || b.x + b.w < a.x ||
                            a.y + a.h < b.y || b.y + b.h < a.y);

      
Note < rather than <=: touching edges count as overlapping,
      which is what a user expects when they drag exactly to the boundary of an icon. The tests
      assert that specific case, because it is the difference between "grazing selects" and
      "grazing does not" and both are defensible until you pick one.


      
3. Set algebra, written as sets

      
function applyModifier(base, hit, mod){
  if (mod === "add")      return new Set([...base, ...hit]);
  if (mod === "subtract") return new Set([...base].filter(id => !hit.has(id)));
  if (mod === "toggle")   return new Set([...base, ...hit]
                            .filter(id => base.has(id) !== hit.has(id)));
  return new Set(hit);                       // replace
}

      
The toggle branch is symmetric difference and it is the one worth reading twice:
      base.has(id) !== hit.has(id) keeps exactly the items in one set but not both.
      Writing it as "remove the intersection from the union" is the same thing and is where people
      drop a case.


      
4. The fuzz, against an independent checker

      
// deliberately NOT the same algorithm: sample the band on a fine grid
function itemsInByProbe(band, items){
  const hit = new Set();
  for (let x = band.x; x <= band.x + band.w; x += 0.5)
    for (let y = band.y; y <= band.y + band.h; y += 0.5)
      for (const it of items)
        if (x >= it.x && x <= it.x + it.w && y >= it.y && y <= it.y + it.h) hit.add(it.id);
  return hit;
}

      
Slow and obviously correct, which is the point of a reference implementation. It cannot
      share a bug with the fast version because it does not share a line with it — and it catches
      the case the AABB test would miss if an inequality were flipped.


      
5. What the tests pin

      
// direction cannot matter
assert(normaliseBand(a, b) deep-equals normaliseBand(b, a));

// the reference agrees, on 40,000 random drags
assert(disagreements === 0);

// naive variants FAIL, or the comparison proves nothing
assert(pathBased.disagreements > 0);
assert(containment.disagreements > 0);

// modifiers are a group-ish structure
assert(applyModifier(base, ∅, "add") deep-equals base);
assert(applyModifier(applyModifier(base, h, "toggle"), h, "toggle") deep-equals base);

      
That last line is the good one: toggling the same set twice must return you exactly where
      you started. It is one assertion and it catches every asymmetry in the symmetric difference.


      
6. And the assertion that the naive versions really are broken

      
A test that the correct implementation passes proves nothing on its own — the comparison
      only means something if the alternatives are shown to fail on the same inputs. So each naive
      variant has an assertion that it disagrees, with the count printed. If a
      "bug" ever stops reproducing, that is a signal the harness has drifted, not that the bug went
      away.
