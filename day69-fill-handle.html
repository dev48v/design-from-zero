DESIGNFROMZERO · DAY 69

🧲 Fill handle — grab the little square, drag it down, get a series. Underneath the drag is one straight line fitted through every selected cell and evaluated at the next position, which is why 1, 2 becomes 3, 4, 5 — and why 1, 2, 4 becomes 5.33 and not 6. That gap is the whole page: the property every fill-handle test asserts — an exact progression continues exactly — is satisfied by seven of seven implementations here on 100.0% of 12,000 clean cases, and so is the sharper property nobody writes down — that filling three cells and then one more equals filling four at once, which holds on 100.0% of every fitted series across all four corpora. Both are blind. Feed the same six wrong versions a column of measured numbers instead of a textbook progression and the two everybody ships — step from the last two cells, step from the first and last — both go wrong on 99.3% of cases, and the last-two-cells one points the trend in the opposite direction on 33.4% of them against 12.0% for the other. 3,642,926 assertions on load against an independently written oracle and an exact BigInt rational fit. Pure vanilla JavaScript, one file, no build step.

Drag the blue square at the bottom-right of the selection. The first column is the correct fill; the other six are one-clause variations, and any cell that disagrees with column one is tinted. Edit the selected cells directly — comma separated — or pick an example.

THIS SELECTION, MEASURED

The fitted line is the one that minimises the squared distance to every selected cell. If you only wanted the last two cells you would have selected the last two cells — that is the entire specification, and it is what makes the answer unique instead of a matter of taste.

THE TWO PROPERTIES EVERYBODY TESTS, ON 12,000 TEXTBOOK PROGRESSIONS

Every seed here is an exact arithmetic progression, so the continuation is known in closed form before any code runs — no oracle needed, the generator picked the step. This is the corpus a fill handle actually gets tested against, and it cannot see a single one of the six defects.

seven of seven pass both. Self-consistent is the stronger test — fill three cells, add them to the selection, fill one more, and check it matches the fourth cell of a single four-cell fill — and it is not luck that everything passes it: adding points that already sit on the fitted line cannot move the fitted line, so the property is a theorem for the correct version and an accident for the others.

THE SAME seven, ON 12,000 COLUMNS OF MEASURED NUMBERS

A trend plus noise — the shape of every real column anyone has ever dragged a fill handle down. Nothing about the implementations changed. The only thing that changed is that the numbers no longer lie exactly on a line.

A fill is a line, not a step


      
The fill handle looks like repetition. You select some cells, you drag, and more cells
      appear that look like they belong. So the natural implementation is a step: work out
      how much the value goes up by, then keep adding it.


      
That is not what the selection means. Selecting n cells and dragging says
      continue this, and the cells are n observations of a value against a
      position. Continuing them is fitting a line through all n and reading it off one
      position further along:


      
value(x) = intercept + slope · x        // x = 0 .. n-1 are the selected cells
fill k   = value(n + k)                 // dragging down
fill k   = value(-1 - k)                // dragging up


      
With two cells there is exactly one line through them, so the fit and the step agree, and
      every test anyone writes uses two or three cells of a clean progression. With four noisy cells
      there are infinitely many lines and only one that minimises the squared distance to all four —
      and a step from the last two ignores the other two entirely.


      
1. The property everybody tests


      
Search any spreadsheet clone for its fill tests and you will find this:


      
expect(fill(['1','2'], 4)).toEqual(['3','4','5','6']);
expect(fill(['5','10','15'], 2)).toEqual(['20','25']);


      
It is a real property — an exact arithmetic progression continues exactly — and it
      is satisfied by every implementation on this page, correct and broken alike, on
      100.0% of 12,000 generated progressions. It has to be. On a seed that lies
      exactly on a line, the last two cells, the first and last cells, the average of the gaps and
      the least-squares fit all recover the same slope, because the residuals are zero and
      there is nothing left for the estimators to disagree about.


      

        
This is the Day-68 lesson again in a different costume. There the
        generated fixtures had no repeated lines, so two broken diffs scored a flat 0.0%. Here the
        generated fixtures lie exactly on a line, so six broken fills score a flat 0.0%.
        A fixture that is too tidy does not weaken a test suite a little — it can remove its ability
        to distinguish the best answer from the worst one entirely.

      


      
2. And the stronger property that is also blind


      
A better test exists, and it is worth knowing that it does not help either. Fill three
      cells; append them to the selection; fill one more. It should equal the fourth cell of a
      four-cell fill:


      
fill(seed ++ fill(seed, 3), 1)[0] === fill(seed, 4)[3]


      
For the least-squares fit this is a theorem, not a coincidence. The fitted
      line is the unique line whose residuals satisfy Σr = 0 and
      Σx·r = 0. The appended points have residual exactly zero by
      construction, so both sums are unchanged, so the same line is still the minimiser. Every
      shortcut estimator passes it too, for a duller reason: the appended points are spaced by the
      shortcut's own step, so the shortcut recovers its own step. Measured over every fitted series
      in all four corpora: 100.0% of 6,570.


      
It does not hold on the copy path, and that is worth separating rather than
      averaging away. When the selection is not extendable — mixed kinds, or plain text — a fill is
      a cyclic repeat, and the length of the cycle is the selection. Grow the selection and
      you have changed the cycle: x, #42a repeats to
      x, #42a, x, #42a, but from the four-cell block the next cell is x
      where the two-cell block said #42a. Measured: 61.4% of copy-path
      selections are self-consistent, for every implementation on this page including the correct
      one. Nothing is broken — the property simply does not apply to repetition, and a headline
      figure that mixes the two paths together hides that.


      
3. What actually separates them


      
Real columns are noisy. Take five months of sales — 120, 138, 131, 149, 144 —
      and ask for the sixth:


      
least squares      slope +5.9   ->  154.1     the line through all five points
first and last     slope +6.0   ->  150.0     ignores the middle three
last two cells     slope -5.0   ->  139.0     the series now goes DOWN


      
The last row is the one to keep. Two numbers dipped at the end of an otherwise rising
      column, and the fill inverted the direction of the whole series. Across 12,000 measured
      columns that happens on 33.4% of them. There is no error, no warning,
      and the value it produces is perfectly plausible — it is only wrong.


      
The 1, 2, 4 case is the same phenomenon at its smallest. The fit gives
      5.33, the endpoints give 5.5, the last gap gives 6. All three are defensible
      in isolation; only one of them used all three cells you selected. And
      80.5% of correct fills over integer data come out fractional, which is
      the single most reported "bug" in this entire component and is not one.


      
4. One cell has no slope


      
Fit a line to a single point and the slope is undefined — there is no spread in
      x to divide by. The fit returns zero, and zero slope is a copy. So the
      rule that a lone 5 fills 5, 5, 5 is not a special case bolted on: it
      is what the maths says when the data cannot answer the question.


      
But a lone Item 5 fills Item 6, Item 7, and a lone
      2026-01-05 advances a day at a time. Same absence of information, opposite
      answer. That is a product decision — text with a counter and dates are
      assumed to be sequences, bare numbers are assumed to be constants — and no amount of
      measurement can derive it. It is worth stating out loud in a spec, because it is the one rule
      here that a reviewer cannot check against anything.


      
5. The other half of the job: putting the number back


      
The fit gives you a number. The cell wants whatever it held before. Three of the six
      defects on this page live entirely in that translation and are unreachable from any numeric
      test:


      
    
        
  • Which number moves. Step 2 of 7 continues as
        Step 2 of 8. The number that advances is the trailing run of digits,
        which needs the regex /^(.*\D)?(\d+)$/ — a greedy prefix forced to end on a
        non-digit. Write /(\d+)/ and you increment the first number instead:
        Step 3 of 7, which is wrong and reads perfectly.
    • 
        
  • Padding. frame008 continues as frame009, not
        frame9. The width comes from the anchor cell — the last cell when dragging
        down, the first when dragging up — and only when the digits actually carry a leading
        zero.
    • 
        
  • Wrapping. A month list is a cycle of twelve, so the index needs a
        floored modulo. (-1) % 12 is -1 in JavaScript,
        months[-1] is undefined, and the cell renders the word
        undefined. Dragging up from Jan is the whole test, and it
        is the one direction nobody tries.
    • 
      


      
Cycles also need a step, and a step across a wrap is ambiguous: from Jan to
      Dec is either +11 or −1. This engine unwraps each
      gap to the shorter way round, so Jan, Dec continues Nov, Oct. It is
      a choice, it is stated, and the oracle implements the same choice by a completely different
      route so that agreement means something.


      
5a. And a cycle has one cell that cannot say which list it is in


      
May is the only month whose abbreviation is its own full name. So a cell
      containing May matches both lists, and if the shorter one wins — which it does,
      because a three-letter match is tested first — then the anchor of the selection
      decides the register for everything that follows. Fill down from
      February and you get March, April, May; extend the selection to
      include them and fill again, and the anchor is now May, so the next cell is
      Jun. The series changes register half way down, and every value in it is a
      correct month name.


      
The oracle could not find this, because the oracle implements the same specification and
      agreed with the engine perfectly. The self-consistency property found it — the one
      that separates no implementations at all is the one that caught a real ambiguity in the spec.
      The fix is that the register belongs to the selection, not to the cell: when the anchor is
      ambiguous, walk away from it to the first cell that can only be one of the two. So
      April, May continues June, July and May on its own
      continues Jun, Jul — both presets are in the dropdown on the first tab.


      
6. Two oracles, priced apart on purpose


      
The clean corpus needs no oracle at all: the generator chose a₀ and the
      step, so the answer at any position is a₀ + step · x in
      O(1). That is what makes 12,000 cases free.


      
Everything else is checked against a reimplementation of the same specification that shares
      no expression with the engine — the line comes from the raw normal equations solved by
      Cramer's rule where the engine uses the centred deviation form, and a list index is advanced
      by stepping one position at a time where the engine uses a modulo. On top of that sits an
      exact check: for integer seeds the prediction is a rational number, so it can
      be computed in BigInt with no rounding at all and compared against the
      floating-point answer. Worst deviation observed over 4,000 seeds: 9.5e-10.


      
And the genuinely expensive oracle stays bounded, which is the Day-66 lesson: confirming
      that the fitted line is the minimiser by searching a lattice of nearby lines costs
      hundreds of evaluations per case, so it runs on 40 seeds and the cheap definitional check —
      residual orthogonality, two sums, O(n) — runs on all of them.


      
7. What this leaves out


      
Real fill handles do more. A 2-D drag fills across columns as well as down, and dragging a
      formula translates its relative references instead of fitting anything. Dates step by
      month or by weekday if you ask, which is calendar arithmetic and not linear at all — the
      31 January problem has no correct answer, only conventions. Growth series fit a line to
      the logarithm. Custom lists let you register Q1..Q4 as a cycle, which is why
      Q1 here continues to Q5: without a registered list it is text with a
      trailing number, and that is the right answer for the rules this page implements. And Flash
      Fill is a different program entirely — program synthesis from examples, not extrapolation.


      
One more honest gap: this page specifies the least-squares fit and measures against that
      specification. Which estimator your favourite spreadsheet ships is a separate question that
      nothing here can settle. What is settled is that a fixture made of clean progressions
      cannot tell any of these implementations apart, and that the two shortcuts diverge on real
      data badly enough to reverse a trend.


    

  






  

    


      
🔨 How it is built


      
1. Six pure functions and no DOM

      
classify(s)                      -> {kind:'num'|'date'|'list'|'label'|'text', ...}
analyze(src)                     -> {kind, cls}         // the whole selection
fitLine(v)                       -> {slope, intercept}  // least squares
fillSeries(src, count, dir, opt) -> [{v, s, kind}]      // opt.bug injects one defect
oracleFill(src, count, dir)      -> [{v, s, kind}]      // the independent reimplementation
exactPredict(v, x)               -> {num, den}          // BigInt rational, no rounding

      
Cells go in as strings and come out as {v, s} — a number when the kind is
      numeric, otherwise null — so the fuzz compares numbers numerically with a
      tolerance and text exactly, instead of comparing formatted strings and calling a rounding
      difference a defect.


      
2. The fit, in the form that does not lose precision

      
function fitLine(v){
  const n = v.length, mi = (n - 1) / 2;
  let sv = 0; for (let i = 0; i < n; i++) sv += v[i];
  const mv = sv / n;
  let sxy = 0, sxx = 0;
  for (let i = 0; i < n; i++){ const dx = i - mi; sxy += dx * (v[i] - mv); sxx += dx * dx; }
  const slope = sxx > 0 ? sxy / sxx : 0;          // n === 1 lands here: no slope exists
  return { slope: slope, intercept: mv - slope * mi };
}

      
Centred deviations, not raw sums of squares — the raw form subtracts two large nearly-equal
      numbers and loses digits. The oracle deliberately uses the raw form so the two disagree in the
      last bits and nowhere else, which is the point of having an oracle.


      
3. Six defects, one clause each

      
last:   slope = v[n-1] - v[n-2]                 // ignore every earlier cell
ends:   slope = (v[n-1] - v[0]) / (n - 1)      // ignore every middle cell
lone:   n === 1 && kind === 'num' ? step 1 : step 0
lead:   /^(\D*)(\d+)([\s\S]*)$/                // the FIRST digit run, not the last
nopad:  padStart(0)                            // width thrown away
rawmod: arr[r % len]                           // -1 % 12 === -1

      
All six are wrappers over the same fillSeries with a bug flag, so
      nothing else can drift between them. The shortcut estimators are also given the most
      favourable possible treatment — their line is anchored to pass exactly through the last
      selected cell, which the least-squares line does not do.


      
4. Four corpora, because one cannot see anything

      
clean  12,000  exact integer progressions      -> closed-form answer, O(1), no oracle
noisy  12,000  trend + jitter, the real shape  -> separates 'last' and 'ends'
lone    6,000  one cell of each kind           -> separates 'lone', nothing else can
labels 12,000  padding, two numbers, cycles,
               and 45% of drags going UP       -> separates 'lead', 'nopad', 'rawmod'

      
Not one of the six defects is visible in the first corpus, which is what a normal test file
      is made of — keep only that one and all six ship. Each of the other three is the only
      corpus that can see something: the trend shortcuts are silent until the numbers stop lying on
      a line, the lone-cell rule cannot be reached by any multi-cell selection, and the three
      formatting defects need padding, a second number in the string, and a cycle that wraps.


      
5. What the tests pin

      
// the correct core agrees with the independent oracle on every case of every corpus
assert(stats.fit.disagree === 0);

// and every broken one passes the property everybody writes
assert(FILL_VARIANTS.every(v => clean.stats[v.key].contOk === clean.stats[v.key].contCases));
assert(fit.selfFitOk === fit.selfFitN);             // theorem, on every FITTED series
assert(fit.selfCopyOk < fit.selfCopyN);            // and provably not on the copy path

// the fit really is the minimiser - bounded, because it is the expensive one
assert(orthogonality(sum_r, sum_xr) < 1e-8);        // O(n), every case
assert(noLatticeLineBeatsIt(41 x 41 grid));         // 40 cases only

// the shortcuts are wrong on data that is not a textbook progression
assert(noisy.stats.last.disagree > 0.5 * noisy.cases);
assert(noisy.stats.last.trendFlips > 0);            // not merely imprecise - inverted

// mean of the gaps IS first-to-last, so they may never disagree
assert(identityStudy(200000).differ === 0);


      
6. What contradicted the first draft

      
Three things, and the third is the one worth having.

      
The plan had average of the gaps as a seventh, separately wrong implementation. It
      is algebraically identical to first and last, so it became a measured identity instead
      of a variant — 200,000 vectors, largest slope difference 1.7e-13, zero
      predictions apart by more than 1e-9.

      
The self-consistency test was written expecting it to be the property that
      separates the implementations. It separates none of them, and the first draft went
      further and claimed it passes everywhere. It does not: 100.0% on every fitted
      series and 61.4% on the copy path, because a cyclic repeat has no such
      property to begin with. Averaging the two into one number would have hidden a genuine
      structural difference behind a plausible-looking 96%.

      
And that same useless property found the only real defect on this page that was not put
      there on purpose. May is its own abbreviation, so it silently switched a series of
      full month names into abbreviations at the boundary. The oracle agreed with the engine
      throughout — both implemented the same ambiguous rule. Re-filling did not. The register is now
      resolved per selection rather than per cell, and the four list self-consistency failures went
      to zero.
