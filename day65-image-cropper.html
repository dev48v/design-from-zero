DESIGNFROMZERO · DAY 65

✂️ Image cropper — a component that looks like drag handles and is really constrained geometry. Three rules have to hold at the same time on every pointer move: the crop stays inside the image, it never shrinks below a minimum, and when a ratio is locked it stays exactly locked. The bug almost every implementation ships is clamping width and height independently when a drag hits the edge — each clamp is individually correct and together they silently break the aspect ratio, so a "1:1" crop exports at 1.06:1 and nobody notices until the avatars look wrong. The fix is to clamp once, on a single scale factor. This page fuzzes the resize against an independently written checker over 20,000 random drags and reports the worst aspect drift for both versions side by side — 1.5 against 4e-16, which is float noise and not a bug. Real canvas export at true source resolution, opposite-corner anchoring, 90° rotation that carries the crop with it, and the minimum-size rule resolved against the ratio rather than after it. Pure vanilla JavaScript, one file, offline.

MINIMUM SIZE vs THE RATIO


        

      


    

  






  

    


      
Three constraints, and they fight


      
A cropper has to satisfy all of these on every single pointer move:


      
    
        
  1. the crop rectangle lies entirely inside the image
    2. 
        
  2. neither side goes below a minimum
    3. 
        
  3. if a ratio is locked, width ÷ height equals it exactly
    4. 
      


      
Each one is trivial alone. Together they are a small constrained-optimisation problem,
      and the order you enforce them in changes the answer.


      
The bug that ships


      
The natural implementation applies the ratio, then clamps:


      
rect.w = Math.min(rect.w, image.w - rect.x);   // keep inside horizontally
rect.h = Math.min(rect.h, image.h - rect.y);   // keep inside vertically


      
Two clamps, each obviously correct. And they silently break the ratio,
      because clamping width and height by different amounts changes w/h.


      

        
The rectangle is still inside the image. It is still above the minimum.
        Every visible constraint holds. The only thing that broke is the invisible one — so it
        passes review, passes a smoke test, and ships. A "1:1" avatar crop exports at 1.06:1 and
        the first person to notice is a designer looking at a grid of faces.

      


      
The fix is to clamp once


      
Because the ratio is fixed, the rectangle has one degree of freedom, not two. So
      compute how much of the requested size actually fits — as a single scale factor — and apply
      it to both sides:


      
const scale = Math.min(1, maxW / want.w, maxH / want.h);
w = want.w * scale;
h = want.h * scale;          // ratio preserved by construction


      
One clamp on one number. The ratio cannot drift because it never becomes two independent
      quantities in the first place. This is the general shape of the fix: when a constraint says
      two variables move together, do not give the code a chance to move them separately.


      
The minimum has the same problem


      
"Neither side below 40px" is also two constraints on one degree of freedom. Under a 2.35:1
      ratio, a 40px minimum on the height forces a 94px width, and a naive
      Math.max(w, 40) on each side produces a 40×40 square that is not 2.35:1 at all.


      
Same answer: convert the minimum into a scale factor and take the larger of the two.


      
Anchoring: the opposite corner does not move


      
Dragging the north-west handle must hold the south-east corner still. Store the anchor when
      the drag starts, not per-frame — recompute it during the drag and the rectangle
      creeps, because each frame anchors to a corner the previous frame already moved.


      
onPointerDown: anchor = oppositeCorner(rect, handle)   // once
onPointerMove: rect = rectFrom(anchor, pointer, ...)  // pure function of the anchor


      
Making the move handler a pure function of the drag-start state is what makes the whole
      thing testable — you can replay 20,000 drags with no DOM at all, which is what this page does.


      
Export in source pixels, always


      
The preview is scaled to fit the layout. If you export the displayed rectangle you export
      a downscaled crop of a downscaled image — throwing away resolution the user still had. The
      crop rect lives in display coordinates; the export multiplies by
      naturalWidth / displayedWidth and reads from the original.


      
It is one multiplication and it is the difference between a 240px avatar and a 1200px one.


      
Rotation is a coordinate change, not a filter


      
Rotating 90° swaps the image's width and height, so a crop expressed in the old frame is
      meaningless in the new one. Either map the rect through the same rotation, or reset it.
      Leaving it as-is produces a crop that is inside the old bounds and outside the new ones — the
      one case where all the clamping logic never runs, because nothing moved.


    

  






  

    


      
🔨 How it is built


      
1. The resize is a pure function

      
resizeRect({ anchor, pointer, handle, ratio, bounds, min })  ->  { x, y, w, h }

      
No element, no event, no state. Everything the DOM layer knows is passed in and a
      rectangle comes back — which is why the fuzz harness can run 20,000 drags in a few
      milliseconds under node with no browser at all.


      
2. Ratio first, as one scale factor

      
// how big could it be from this anchor, in this direction?
const maxW = dirX > 0 ? bounds.w - anchor.x : anchor.x;
const maxH = dirY > 0 ? bounds.h - anchor.y : anchor.y;

let w = Math.abs(pointer.x - anchor.x);
let h = ratio ? w / ratio : Math.abs(pointer.y - anchor.y);

if (ratio){
  const grow = Math.max(1, min / w, (min / ratio) / h);   // minimum, as a scale
  w *= grow; h *= grow;
  const fit = Math.min(1, maxW / w, maxH / h);            // bounds, as a scale
  w *= fit; h *= fit;
} else {
  w = Math.min(Math.max(w, min), maxW);                   // free ratio: independent IS correct
  h = Math.min(Math.max(h, min), maxH);
}

      
The else branch is the tell. With no ratio the two axes really are
      independent and clamping them separately is right — which is exactly why the bug survives:
      the wrong code is the correct code for the mode people test first.


      
3. Order matters, and it is minimum-then-bounds

      
Grow to the minimum first, then shrink to fit. The reverse can leave a rectangle that
      satisfies the minimum and hangs outside the image, because the growth step has nothing after
      it to catch the overflow.

      
When the image is genuinely too small to hold the minimum at that ratio, the fit step wins
      and the result is smaller than the minimum. That is the honest outcome — the alternative is a
      rectangle outside the image — and the function returns it rather than pretending.


      
4. The anchor is captured once

      
const OPPOSITE = { nw:'se', ne:'sw', se:'nw', sw:'ne', n:'s', s:'n', e:'w', w:'e' };

function cornerOf(r, which){
  const x = which.includes('w') ? r.x : which.includes('e') ? r.x + r.w : r.x + r.w / 2;
  const y = which.includes('n') ? r.y : which.includes('s') ? r.y + r.h : r.y + r.h / 2;
  return { x, y };
}

      
Edge handles map to a midpoint, which is what makes n and s fall
      out of the same code path as the corners instead of needing their own branch.


      
5. The fuzz harness, and what it asserts

      
for (let i = 0; i < 20000; i++){
  const r = resizeRect(randomDrag());
  assert(r.x >= -EPS && r.y >= -EPS);
  assert(r.x + r.w <= bounds.w + EPS);
  assert(r.y + r.h <= bounds.h + EPS);
  if (ratio) drift = Math.max(drift, Math.abs(r.w / r.h - ratio));
}

      
Three containment assertions and one drift measurement. The containment assertions pass
      for both implementations — that is the finding. Only the drift number separates
      them, and only because something is watching it.


      
6. Export maps display coordinates to source pixels

      
const k = img.naturalWidth / stage.clientWidth;
ctx.drawImage(img,
  crop.x * k, crop.y * k, crop.w * k, crop.h * k,   // source rect, real pixels
  0, 0, out.width, out.height);                     // destination


      
One scalar, applied to four numbers. Forget it and the export is silently correct-looking
      and a third of the resolution — the kind of bug that never throws and never gets reported,
      it just makes everything slightly worse.
