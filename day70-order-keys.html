DESIGNFROMZERO · DAY 70

🃏 Order keys — drag a card and one row is written, whichever column it came from and however long the list is. Every card carries a base-62 string read as a fraction, so between any two keys there is always another key, and a move is a single UPDATE of the card you dragged. That "one row" is the whole page, because the property every reorder test asserts — after the drop, every card is where you put it — is satisfied by five of the eight implementations here on 100.0% of 6,000 random moves and 100.0% of 6,000 moves shaped like a real board. Two of those five lose the board on moves 45 and 55 of one ordinary habit — dropping a card just under the pinned one at the top — and the other two are never wrong in any column and pay for it in writes, 6.5 rows per move for one of them and a whole-column rewrite whenever a gap runs out for the other. And the loudest defect on the page is not in any of the code — it is the collation on the ORDER BY, which reorders 9.5% of key pairs and gets the board wrong before a single card has moved. 3,974,372 assertions on load against an order written as a bare array of ids, an exact BigInt fraction comparison and an independently built midpoint. Pure vanilla JavaScript, one file, no build step.

THE BUDGET, WHICH IS NOT A NUMBER YOU CAN LOOK UP

A float64 position can be halved a fixed number of times before the midpoint is one of its neighbours — and that number is not a constant, it is the distance between the exponent of the gap and the exponent of the numbers. So the same code survives 1,074 insertions at the head of a new list and 23 next to a timestamp.

SO WHAT DOES A STRING COST INSTEAD

      

        Nothing that fails. The string scheme has no budget at all — it has a
        length, and length is a resource you can keep spending. Three thousand insertions
        into the same gap, every one of them checked as an exact fraction against both neighbours.
      

      

      

    


    

      
THE DEFECT THAT IS NOT IN THE CODE

      

        The keys are right. The generator is right. The comparison is wrong, and the comparison
        lives in the database. A case-insensitive collation — the default one in MySQL
        — is not a coarser version of byte order, it is a different order,
        and base-62 crosses the case boundary on the second key it ever mints.
      

      

      

      

    


    

      
THE ONE INVARIANT, AND WHAT BREAKING IT DOES

      

        x and x0 are the same fraction and two different strings. Allow a
        key to end in the minimum digit and the byte order and the numeric order stop agreeing
        — not occasionally, on every such pair — and the generator can be handed a
        request that has no answer.
      

      

      

    


    

      
TWO PEOPLE, ONE GAP

      

        A key is a function of its two neighbours and nothing else, so two clients inserting into
        the same gap from the same snapshot produce the identical key. Neither is
        wrong. The fix is not in the generator: the identity of a card's position is the
        (key, id) pair, and the tie-break belongs in the ORDER BY.
      

      

      

    


    

      
THREE CONCRETE BOARDS

      

      

      

    


  

  






  

    

      
A position is a fraction, and a string can hold one

      

        Reordering a list looks like the easiest problem in this series. You have a column of
        cards, you drag one, you save. The trouble is entirely in the word save. If a
        card's place in the list is an integer index, then moving one card changes the index of
        every card after it, and a single drag becomes an UPDATE of half the column
        — on every client, over a network, with somebody else dragging at the same time.
      

      

        So instead of an index, give each card a key, and require only that the
        keys sort into the right order. Nothing says the keys have to be dense. If the card above
        holds k and the card below holds s, the dragged card wants
        anything strictly between them, and then exactly one row is written. The whole component
        reduces to one function: keyBetween(lo, hi).
      

      

        Integers cannot do it, because between 3 and 4 there is nothing. Floats can do it 52 times
        and then cannot. A string can always do it, because a string has no last digit:
        read "V" as the base-62 fraction 0.V and "Vk" as 0.Vk, and there
        is always another digit to add.
      


      
1. The property everybody tests

      

        Every test written for this component says the same thing: drag a card, read the list back,
        and check it came out in the order you dropped it. It is the right property. It is also
        satisfied by five of eight implementations on this page over
        6,000 random moves and 6,000 moves shaped like a real
        board — not approximately, on 100.0% of them.
      

      

        Two of those five are wrong in a way the property cannot express, because they keep the
        positions dense: one renumbers the column on every single move, at
        6.5 rows written per move, and one leaves gaps of a thousand and
        renumbers only when a gap runs out. A test that reads the list back sees a perfect list from
        both. Only a test that counts writes sees anything at all — and nobody writes that
        test, because "how many rows did that touch" does not feel like correctness until the day
        the board has 400 cards on it and two people are dragging.
      

      

        The other two are correct until they are not. A float64 position and a key read
        back as a float both work perfectly on every move a random fuzz will ever generate, and
        both fall over inside the first hundred moves of one specific habit. Which brings up the
        thing this page kept running into.
      


      
2. The corpus decides what you can see

      

        I built the four op streams expecting the realistic one to be the sharp instrument —
        Day 68 and Day 69 both turned on the fact that a generated fixture is too tidy to contain
        the defect, so the plan here was to put the breaking structure into the realistic corpus
        and let it do the work. It did not work. Six thousand moves of nudges, promotions and
        handoffs between columns fail to break a float64 position even once.
      

      

        What breaks it is one habit in isolation: a pinned card stays at the top of the column and
        everything urgent gets dropped directly underneath it. That reuses the same gap every
        single time, and the gap halves every single time, and on move 55
        the midpoint of the two neighbours is the lower neighbour. The realistic mixture
        contains that habit — a quarter of its moves are exactly it — and still never
        triggers it, because between two of those moves something else lands in the gap and resets
        it.
      

      

        So the lesson is narrower than "make the fixture realistic". A defect with a budget is only
        visible to a corpus that spends the budget in one place. Averaging over realistic
        behaviour is the same as hiding it.
      


      
3. What the string actually has to guarantee

      

        Two things, and the second one is the one that gets skipped.
      

      
    
        
  • Between-ness. keyBetween(lo, hi) returns a key whose
          fraction is strictly greater than lo and strictly less than
          hi.
    • 
        
  • That the fraction order and the byte order are the same order. Nothing
          ever compares fractions at runtime. The database compares bytes. If those two orders can
          disagree on even one pair of keys, the scheme is not an order.
    • 
      

      

        The second holds for free in one direction: if two keys first differ at position
        i, the digit that differs is worth at least 62−(i+1) and
        everything after it is worth strictly less than that, so the byte comparison and the
        fraction comparison agree. The direction that does not come free is a key that is
        a prefix of another. "A2" and "A20" are the same fraction and two
        different strings, so byte order says one is smaller and arithmetic says they are equal.
      

      

        One rule fixes it: a key never ends in the minimum digit. Then a longer
        key that extends a shorter one is always strictly greater, and the two orders coincide
        everywhere. This page checks that on 20,000 random key pairs
        against exact BigInt fractions — 0 disagreements — and then appends a
        0 to each of them and gets a disagreement on 100.0%.
      


      
4. Your ORDER BY is part of the algorithm

      

        This is the defect I expected to be subtle and which turned out to be the loudest thing on
        the page. The keys are correct. The generator is correct. The comparison that reads them
        back is a case-insensitive collation, which is the default in MySQL, and a case-insensitive
        collation is not a coarsening of byte order — it is a different total order.
        Byte order puts every uppercase letter before every lowercase one; case-insensitive order
        interleaves them. V and k come out in opposite
        orders, and those are literally the first two keys a fresh column is seeded with.
      

      

        So the board is wrong before anybody drags anything, on
        100.0% of boards. Except under one habit: a workload that only
        ever inserts at the top drives the keys down into the digits, where the two collations
        agree, and the same defect shows up on 5.6% of those sessions.
        The visibility of the bug is a property of your users' habits, not of your code.
      

      

        And it is not only a rendering problem. The generator asks the store for the two cards
        either side of the drop, so a wrong ORDER BY hands it the wrong neighbours and
        it mints a key that is not between the cards it will actually sit between —
        1,234 such keys over 6,000 moves. The fix is a binary collation
        on the column, or an alphabet that never mixes case. Base-36 lowercase costs you about 1.2
        characters of key length per level and removes the entire failure mode.
      


      
5. And a key read back as a number is a string that was thrown away

      

        A base-62 digit carries log₂62 ≈ 5.95 bits, so a key of 9 digits is already
        past the 53 bits a double has. Decode the keys and sort numerically and everything is fine
        until keys get long — the first pair that lands on the same double appears at
        insertion 44, at key length 10,
        exactly where the arithmetic says it should. After that the sort has nothing to order by
        and falls through to whatever the tie-break is.
      

      

        This is the same failure as the float64 position, arrived at from the opposite direction:
        one stored a number and ran out of precision, the other stored a string and threw the
        precision away on read. The string is only unbounded if you never convert it.
      


      
6. Two clients produce the same key, and that is fine

      

        keyBetween is a pure function of its two arguments, so two people dropping a
        card into the same gap at the same moment generate the identical key
        — 100.0% of the time, by construction, not by accident.
        Neither client is wrong and no amount of care in the generator prevents it.
      

      

        Sort by key alone and the two clients render the two cards in opposite orders, and both
        orders are stable, so nothing ever converges: 100.0% of those
        sessions diverge. Sort by (key, id) and every client agrees, on
        0 divergences over 4,000 sessions, because the id is a value both
        clients already have and neither invents.
      

      

        The general shape: the key is not the identity of a position. The pair is. Adding random
        noise to the key instead is the tempting alternative and it is unsound — a suffix can
        push a key past the upper bound it was generated against, which is a much worse failure
        than a tie.
      


      
7. Two oracles, priced apart on purpose

      

        The order oracle is an array of ids. It has no keys, no arithmetic, no
        comparison and no idea what a fraction is: to move a card it filters the array and splices
        it. It is O(n) per move, which is what makes 13,600 moves × 8 implementations
        affordable, and it shares not one line with anything it is checking.
      

      

        The expensive oracle is the arithmetic one: decode both bounds into BigInt integers over a
        common denominator, take the integer midpoint, encode it back. It answers a different
        question — not "is this the key the generator returns" but "is there a key here at
        all, and is the one you returned really between the bounds" — and it costs a BigInt
        division per call, so it runs on a bounded 20,000 pairs rather than inside the fuzz.
      


      
8. What this leaves out

      

        Keys grow. Under the pathological habit they grow at about one character per five
        insertions, and a board hammered that way for years wants an occasional background
        rebalance that rewrites the column with short keys — the one operation this scheme
        has that is not O(1), performed when nobody is looking rather than on every drag. Real
        systems also add an integer part in front of the fraction (Figma, and Jira's LexoRank)
        precisely so that appending at the end never lengthens anything; that is a second mechanism
        and this page has one.
      

      

        Nothing here is authorisation, undo, or the animation of the drag itself. And the board
        deliberately has no server: every measurement is about what would be written, not about
        what happens when the write fails.
      

    

  






  

    

      
🔨 How it is built


      
1. Six pure functions and no DOM

      

        Everything between ENGINE:BEGIN and ENGINE:END is pure. The
        generator is keyBetween; the reader is byteCmp; the invariant is
        validKey; the arithmetic is keyNum and exactCmp in
        BigInt; the board is applyMove over an array of
        {id, col, k}; the truth is truthMove over an array of ids. The
        verifier lifts that block out of the page by regex, refuses it if it mentions
        document, and runs it under node against assertions written separately.
      


      
2. keyBetween, in three branches

      

        Walk the two bounds digit by digit, with '' standing for the fraction 0 and
        null for 1. Digits both bounds agree on are not a decision — copy them,
        padding the low bound with the minimum digit, because a shorter key is the same fraction
        with zeros after it. At the first digit where they differ there are three cases: a digit
        fits between them, so take the middle of the free range; they are consecutive but the upper
        bound has more digits after it, so the upper bound's own digit is already strictly below
        it; or neither, in which case keep the low bound's digit and look one place further right
        with the upper bound dropped. The loop terminates because the low bound is finite: once you
        walk past its end there are 62 digits of room.
      


      
3. Eight implementations, one clause each

      

        The board, the op stream, the tie-break on id and the assertions are shared. Each
        implementation changes exactly one thing: how a position is minted
        (float, dense, gap), which comparison reads it back
        (ci, numsort), when the neighbours are read
        (idx), or one clause inside the generator (prefix, which
        compares the shared prefix without padding the low bound). Every one of them is a thing
        that ships.
      


      
4. Four op streams, because one cannot see anything

      

        anywhere is the fuzz you would write. a real board mixes nudges within a
        column, promotions to the second slot, handoffs to the next column and appends to the
        bottom. to the top and under the top are single habits in isolation. All
        four are generated from the oracle's state, never from any
        implementation's keys, so all eight see byte-for-byte the same session — and the
        table only differs between columns because of which gaps get used.
      


      
5. What the tests pin

      
    
        
  • Every card in every column against an array of ids, after every move, for all eight.
    • 
        
  • Every generated key strictly between its two neighbours, as exact BigInt fractions.
    • 
        
  • Every key valid: in the alphabet, non-empty, and not ending in the minimum digit.
    • 
        
  • Byte order against exact fraction order on 20,000 random pairs, and the same 20,000
          with the invariant deliberately broken.
    • 
        
  • The generator's key and an independently built BigInt midpoint both strictly between
          the same bounds, on every pair.
    • 
        
  • Rows written per move, collisions, renumbers and longest key, per implementation.
    • 
        
  • The same seed gives the same session; a different seed does not.
    • 
      


      
6. What contradicted the first draft

      
    
        
  • The plan was to put the breaking structure into the realistic corpus. It is not enough:
          6,000 realistic moves never exhaust a float64 position, even though a quarter of them are
          the habit that does. A budget is only visible to a corpus that spends it in one place.
    • 
        
  • The collation defect was drafted as the subtle one and is the loudest thing here, because
          base-62 crosses the case boundary on the second key it mints. Its visibility inverts under
          a top-insert workload, where it drops to 5.6%.
    • 
        
  • Integer gaps of 1,000 were drafted as a constant tax and are not: they renumbered
          2 times in 6,000 realistic moves. The reason to reject them is
          the tail, not the mean.
    • 
        
  • The classic off-by-one — reading the drop neighbours before the dragged card
          leaves — is invisible to a suite that only ever drags to the top, at
          0.0% there against 95.4% on a real board.
    •
