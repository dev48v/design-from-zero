DESIGNFROMZERO · DAY 67

🗓️ Day-view event layout — the calendar column that puts overlapping meetings side by side. Underneath, it is interval-graph colouring: cluster the day, give every event the lowest free column, then let each one expand rightwards over the columns nothing blocks. That greedy pass is optimal — but only in start-time order, and nothing on screen tells you when you got it wrong, because a layout using too many columns still never overlaps. That is the trap: the one property everyone tests is satisfied by four of the six wrong versions here — the real defects are narrower, not broken. Intervals are half-open, so 10:00–11:00 and 11:00–12:00 do not collide; get that wrong and a day of back-to-back meetings silently halves its own width. Fuzzed against two independently written oracles over 12,000 random schedules. Pure vanilla JavaScript, one file, offline.

Drag an event to move it, or drag its bottom edge to resize — everything snaps to 15 minutes and the whole day re-lays out on every frame. Switch the algorithm and watch what changes: red boxes are ones an independent checker found sitting on top of something they overlap in time.

THIS DAY, MEASURED

columns used comes from the layout. most at once comes from a sweep line that knows nothing about the layout. When they are equal the layout is provably optimal — an interval graph needs exactly as many columns as its busiest moment, never one more.

A calendar column is a graph colouring problem


      
Each event is an interval. Two events that overlap in time may not share horizontal space.
      Give every event a colour so that no two adjacent intervals share one, and use as few colours
      as possible: that is exactly graph colouring on an interval graph, and the
      colours are your columns.


      
Interval graphs are perfect, which has a very concrete payoff here: the smallest
      number of columns you can possibly need equals the largest number of events happening at the
      same instant. Not an approximation — an identity. So there is an oracle for the column count
      that shares no code at all with the layout: sweep the endpoints, count up on a start and down
      on an end, and take the maximum.


      
function maxConcurrency(events){
  const pts = [];
  for (const e of events){ pts.push({t:e.start, d:+1}); pts.push({t:e.end, d:-1}); }
  pts.sort((p,q) => p.t - q.t || p.d - q.d);   // ends before starts at equal t
  let cur = 0, mx = 0;
  for (const p of pts){ cur += p.d; if (cur > mx) mx = cur; }
  return mx;
}


      
That || p.d - q.d is the half-open rule again: at 10:00 the meeting that ends
      must be counted out before the meeting that starts is counted in, or a day of back-to-back
      meetings reports two at once.


      
1. Half-open intervals, decided once


      
An event runs [start, end). 10:00–11:00 and 11:00–12:00 do not overlap.


      
const overlaps = (a, b) => a.start < b.end && b.start < a.end;   // NOT <=


      
Write <= and nothing breaks visibly — the layout is more
      conservative, so it can never produce a collision. It just puts every meeting in a day of
      back-to-back meetings into two columns instead of one and halves the width of the entire day.
      Over 12,000 random schedules the closed-interval version needed extra columns on more than a
      quarter of them, and produced zero overlaps on all of them.


      
2. Cluster against the running maximum end


      
Events are grouped into clusters — maximal runs that are connected by overlap — because the
      column count is per cluster, and a fresh cluster resets to full width. Sorted by start, an
      event joins the current cluster if it starts before the latest end seen so far.


      
let maxEnd = -Infinity;
for (const e of sorted){
  if (cluster.length && e.start >= maxEnd) { flush(); }
  cluster.push(e); maxEnd = Math.max(maxEnd, e.end);   // running MAX, not e.end
}


      

        
Compare against the previous event's end instead and one long
        event stops holding its cluster together. A 09:00–17:00 all-hands with two short meetings
        inside it splits after the first, the second gets a cluster of its own and full width, and
        the two are drawn on top of each other. This is the one broken version that fails loudly —
        41% of random days.

      


      
3. Greedy is optimal, in exactly one order


      
Place events one at a time into the lowest-numbered column with nothing conflicting in it.
      Sorted by start time this is provably optimal: when you place an event, everything already
      placed that conflicts with it is live at that instant, so those events pairwise overlap each
      other too and occupy that many distinct columns. You land in column k only when
      k events are already running, and the sweep line says the same thing.


      
Take the sort away and the argument evaporates. Four meetings, never more than two at once:


      
11:15-12:15   11:45-13:00   12:45-13:45   13:30-15:00

by start time :  2 columns, 0 overlaps
in array order:  3 columns, 0 overlaps  <- both are "correct"


      
Both layouts pass every collision test you can write. Three of the four meetings come out a
      third narrower, and the mean width across the day falls from half the lane to 41.7% of it. This
      is why the ordering line is the one that gets refactored away in a cleanup — it looks
      decorative, and removing it breaks nothing you can see.


      
4. Expansion, and why it must be checked


      
An event in column 0 of a three-column cluster gets a third of the lane even if columns 1
      and 2 are empty for its entire duration. So after assignment each event expands rightwards,
      stopping at the first column that holds something it overlaps in time.


      
let span = 1;
for (let c = e.col + 1; c < ncols; c++){
  if (cluster.some(o => o !== e && o.col === c && overlaps(o, e))) break;
  span++;
}


      
Drop the overlaps check and take ncols - e.col instead — the
      obvious simplification, and it destroys the layout: 95% of random days come out with boxes on
      top of each other. Drop expansion altogether and nothing is ever wrong; it simply touches
      6.2% of events, and those end up 2.7× wider. That is the
      honest size of the feature, and it is smaller than it feels: expansion is a whole-event
      property, so one blocked minute anywhere in a meeting stops it expanding for its entire
      duration, and in a dense cluster almost every minute is blocked somewhere.


      
What is deliberately left out


      
All-day events live in their own strip above the grid and are not intervals in this sense.
      Events that cross midnight need splitting per day before any of this runs. A minimum height for
      a 5-minute meeting breaks the clean mapping from time to pixels and has to be applied after
      layout, never before, or short events start colliding for real. And DST means a "day" is
      sometimes 23 or 25 hours long — a reason to lay out in minutes-from-day-start rather than in
      timestamps.


    

  






  

    


      
🔨 How it is built


      
1. Four pure functions and no DOM

      
clusters(sortedEvents)              -> Event[][]
assignColumns(cluster, order)       -> number of columns  (sets e.col)
expandSpan(e, cluster, ncols)       -> number of columns e may span
layout(events, opts)                -> { items:[{left, width, ...}], columns }

      
left and width come out as fractions of the lane, so the DOM layer
      is two lines of percentage arithmetic and everything above it can be fuzzed under node.


      
2. The conflict test is over the whole column

      
for (c = 0; c < cols.length; c++)
  if (!cols[c].some(o => overlaps(o, e))) break;   // first column with no conflict

      
The tempting optimisation is to keep one colEnd[c] per column and test
      colEnd[c] <= e.start. That is correct only while the input is sorted by
      start — which makes the sort load-bearing in a second, invisible way. Testing the whole column
      costs nothing at calendar sizes and keeps the ordering question isolated to one line, which is
      what makes the ordering variants measurable here at all.


      
3. Two oracles, neither of which shares a line with the layout

      
// (a) does the layout use the right NUMBER of columns?
//     sweep line over endpoints - knows nothing about columns
maxConcurrency(events) === layout(events).columns

// (b) do the rectangles it produced actually avoid each other?
//     the layout never asks this question anywhere, so it is a real check
for each pair (a, b):
  if (a.start < b.end && b.start < a.end)          // overlap in TIME
    assert(!(a.left < b.left + b.width &&
             b.left < a.left + a.width))             // must be disjoint in X

      
Oracle (b) is the important one philosophically: non-collision is never computed by the
      layout, it is a consequence of the column assignment. Checking it is genuinely testing
      the algorithm rather than restating it.


      
4. And a third one that is far too slow to use

      
// paint the day into (minute-slot x lane-slot) cells, sampling cell CENTRES so
// rounding cannot invent a collision, and count cells claimed twice.
function occupancyCollisions(items, T, X, dayStart, dayEnd){
  for (let t = 0; t < T; t++){
    const tm = dayStart + (t + 0.5) * (dayEnd - dayStart) / T;
    for (let x = 0; x < X; x++){
      const xx = (x + 0.5) / X;
      let n = 0;
      for (const it of items)
        if (tm >= it.start && tm < it.end && xx >= it.left && xx < it.left + it.width) n++;
      if (n > 1) clashes++;
    }
  }
}

      
Obviously correct, and O(T · X · n) per schedule — thousands of times slower
      than the pairwise form. It runs on a bounded handful of cases as a check on the oracle,
      never inside the fuzz. A reference implementation you cannot afford to run everywhere is still
      worth writing; it just has to be aimed at the checker rather than at the code under test.


      
5. What the tests pin

      
// the column count is exactly the busiest instant, on every schedule
assert(layout(ev).columns === maxConcurrency(ev));

// nothing overlaps, ever
assert(overlapReport(layout(ev).items).collisions === 0);

// every box is inside the lane
assert(items.every(i => i.left >= 0 && i.left + i.width <= 1));

// and the broken versions really are broken, on the same inputs
assert(pairwiseClustering.collisionCases > 0);
assert(arrayOrder.extraColumnCases > 0);
assert(arrayOrder.collisionCases === 0);        // <- the point of the whole page


      
6. The assertion that matters most is the last one

      
A wrong version that fails the obvious test is not dangerous; it never ships.
      Asserting that the array-order and closed-interval variants produce zero
      collisions is asserting that the obvious test cannot find them — which is the reason to
      measure column counts and widths at all. If that assertion ever starts failing, the harness has
      drifted, not the bug.
