DesignFromZero · Day 61

Emoji picker — a Slack/Notion-style picker where one dataset array drives every pixel. Nothing is hardcoded per render: the categories, the rail, the row count, the search results and the preview all fall out of {char, name, keywords, group}. Search is a pure tiered ranker, not a fuzzy score — the query is normalised once, then every entry gets the best tier it can reach (exact name → name word-start → keyword word-start → substring anywhere) and results sort by tier, then name length, then dataset order, so hea puts heart above heart on fire and never above a plain substring hit. The grid is genuinely windowed: a ResizeObserver measures the width, the column count comes from that measurement, the row count is derived from it, and only the rows the viewport can actually see exist in the DOM — found with a binary search over a cumulative offset array that mixes short header rows with taller emoji rows. The category rail scroll-syncs both ways, and the sticky header is computed from the real scrollTop and gets pushed up by the next one. And the Unicode is real, not described: long-press any hand or person for the five Fitzpatrick modifiers (U+1F3FB–U+1F3FF) inserted after the base code point with the redundant VS16 dropped — while the live inspector prints the true [...str] code points and the Intl.Segmenter grapheme count, so a family ZWJ sequence reads as 1 grapheme and 7 code points. Picks are ranked by real frecency (a decayed frequency recomputed on every pick), the keyboard drives a 2-D cursor over the virtual grid with role="grid" and roving tabindex, and the chosen emoji is inserted at the caret of a contenteditable through the Selection/Range API — not appended to the end. No libraries, no images — every icon is inline SVG.

One array, a tiered ranker and a windowed grid — a picker that really searches.

Type in the search box — try hea, fire, lol or rocket — and watch the match count and the tier breakdown change on every keystroke. Long-press (or hover) a hand like 👋 or 👍 for the five skin tones, then read the inspector: the modifier is inserted after the base code point, not appended. Click the family 👨‍👩‍👧‍👦 and the inspector shows 7 code points, 1 grapheme. Use the keyboard: / focuses search, ←↑→↓ move a 2-D cursor that wraps across rows, Enter picks, Esc closes and returns focus to the trigger. Put the caret in the middle of the message and pick — the emoji lands at the caret, not at the end. Pick a few and the Frequently used row reorders itself by frecency.

An emoji picker looks like a decoration and is actually a compressed course in three things every product eventually needs: ranking a big list from typed text, drawing only what fits, and treating text as graphemes rather than characters. Get those three right once and autocomplete, command palettes and mention menus are the same component wearing different clothes. Tomorrow: Linear command bar — fuzzy filter and keyboard hints.

🔨 Build it yourself

    
An emoji picker is three problems stacked on one array. First data: a flat list of {char, name, keywords, group} normalised once at load, so nothing downstream ever lowercases anything again. Then ranking: a pure function that gives an entry the best tier it can reach and a sort with deterministic tie-breaks, which is far more predictable than a fuzzy score nobody can explain. Then drawing: a measured column count, a derived row count, a cumulative offset array and a binary search, so only the visible rows exist. Underneath all of it sits real Unicode — VS16, ZWJ and the five skin-tone modifiers — which is why an emoji is a grapheme, not a character. Vanilla HTML, CSS and JS — no framework, no dependencies, no emoji library.

    
    

      
  1. 
        
    1
    The dataset is the component
    
        
    Every category tab, every rail icon, every row and every search result has to come from one array or you will end up maintaining the same list in four places. Write the source in the most compact shape a human can edit — character, name, a space-separated keyword string — then expand it once into objects that carry the normalised fields and the original index. That index is not decoration: it is the final tie-break that makes the ranking deterministic.
    
        
    const RAW = [
  { name:"Smileys & Emotion", icon:"\u{1F600}", rows:[
    ["\u{1F600}", "grinning face", "smile happy joy grin"],
    ["\u{1F602}", "face with tears of joy", "lol laugh cry funny"],
  ]},
  /* ...eight more groups... */
];

let seq = 0;
const GROUPS = RAW.map((g, gi) => ({
  name: g.name, icon: g.icon, gi,
  items: g.rows.map(([char, name, kw]) => ({
    char, name, group: g.name, gi,
    keywords: kw ? kw.split(" ") : [],
    nname:    normalize(name),        // normalised ONCE, at load
    nkw:      normalize(kw || ""),
    i:        seq++                   // stable dataset order
  }))
}));
const EMOJI = GROUPS.flatMap(g => g.items);

    2
    Normalise both sides, exactly once
    
        
    Users type :JOY:, heart_eyes and 1st; the dataset says face with tears of joy and 1st place medal. Rather than sprinkling toLowerCase() through the matcher, define one normaliser and run it over the names and keywords at load and over the query on each keystroke. Keep hyphens and digits — heart-eyes, jack-o-lantern and 1st are real tokens — and turn colons and underscores into spaces so shortcode habits keep working. Collapse runs of whitespace at the end so "  red   heart " and "red heart" are the same query.
    
        
    function normalize(s){
  return String(s)
    .toLowerCase()
    .replace(/[_:]+/g, " ")         // :heart_eyes: -> heart eyes
    .replace(/[^a-z0-9 +-]+/g, " ") // keep digits, hyphen and plus
    .replace(/\s+/g, " ")
    .trim();
}

    3
    Tiers, not fuzzy scores
    
        
    A single numeric score forces you to invent weights, and then nobody — including you — can explain why one emoji beat another. Give each entry the best tier it can reach instead: an exact name is 0, a word inside the name starting with the query is 1, a keyword starting with the query is 2, and a substring anywhere is 3. The word-start test is one line if you prepend a space to both sides, and because the tiers are ordered you get a hard invariant you can actually assert in a test: no tier-2 hit ever appears above a tier-1 hit.
    
        
    const T_EXACT = 0, T_NAME = 1, T_KEY = 2, T_SUB = 3, T_NONE = 99;

function tierOf(e, q){
  if (!q) return T_NONE;
  if (e.nname === q)                       return T_EXACT;
  if ((" " + e.nname).includes(" " + q))   return T_NAME;  // word-start
  if ((" " + e.nkw).includes(" " + q))     return T_KEY;
  if (e.nname.includes(q) || e.nkw.includes(q)) return T_SUB;
  return T_NONE;
}

  4. 
        
    4
    Deterministic tie-breaks make search feel stable
    
        
    Inside a tier there will be dozens of equals, and if you leave the order to chance the list reshuffles as you type and the first result — the one Enter picks — becomes a lottery. Break ties by name length first, because the shortest name containing your query is almost always the thing you meant (hea → red heart before heart on fire), then by the original dataset index so the result is fully determined. Keep the whole thing a pure function of (query, dataset) with no reads of component state, and it becomes trivially unit-testable against a brute-force scorer.
    
        
    function searchEmoji(query, data){
  const q = normalize(query);
  if (!q) return [];
  const hits = [];
  for (const e of data){
    const t = tierOf(e, q);
    if (t !== T_NONE) hits.push({ e, t });
  }
  hits.sort((a, b) =>
       a.t - b.t                            // tier wins
    || a.e.nname.length - b.e.nname.length  // then shortest name
    || a.e.i - b.e.i);                      // then dataset order
  return hits.map(h => h.e);
}

    5
    An emoji is a grapheme, not a character
    
        
    "\u{1F468}‍\u{1F469}‍\u{1F467}‍\u{1F466}".length is 11, [...str].length is 7, and what the user sees is 1. Those are three different questions: UTF-16 units, code points, and user-perceived characters. Never slice emoji with string indexes; iterate with the spread operator to get code points and use Intl.Segmenter when you need the count a human would give. Build the inspector early — once you can see the real code points, VS16, ZWJ and the tone modifiers stop being folklore.
    
        
    const SEG = new Intl.Segmenter(undefined, { granularity:"grapheme" });

function inspect(str){
  const cps = [...str].map(c => c.codePointAt(0));   // NOT str.split("")
  return {
    codePoints: cps,
    hex:        cps.map(c => "U+" + c.toString(16).toUpperCase().padStart(4, "0")),
    units:      str.length,                          // UTF-16 units
    graphemes:  [...SEG.segment(str)].length,        // what a human counts
    hasZWJ:     cps.includes(0x200D),
    hasVS16:    cps.includes(0xFE0F)
  };
}

  6. 
        
    6
    Skin tones: insert after the base, drop the VS16
    
        
    A skin tone is not a suffix. The five Fitzpatrick modifiers U+1F3FB–U+1F3FF must follow the code point they modify, which is the first one with the Emoji_Modifier_Base property — and you do not need a hand-written table for that, because JS regular expressions expose the property directly. Two rules complete it: a modifier already implies emoji presentation, so a U+FE0F sitting right after the base becomes redundant and is removed; and only sequences with exactly one modifier base can be toned this way, which is why a family of four gets no flyout. Verify with the segmenter — if the result is still one grapheme, you inserted it in the right place.
    
        
    const TONES = [0x1F3FB, 0x1F3FC, 0x1F3FD, 0x1F3FE, 0x1F3FF];
const MODBASE = /\p{Emoji_Modifier_Base}/u;          // the Unicode table, free

const baseIdxs = cps => cps.map((c, i) => [c, i])
  .filter(([c]) => MODBASE.test(String.fromCodePoint(c))).map(([, i]) => i);

function toneCapable(str){
  const cps = [...stripTone(str)].map(c => c.codePointAt(0));
  return baseIdxs(cps).length === 1;                 // single-person only
}

function applyTone(str, tone){                       // tone: 0 = default
  const cps = [...stripTone(str)].map(c => c.codePointAt(0));
  const at  = baseIdxs(cps)[0];
  if (!tone || at === undefined) return String.fromCodePoint(...cps);
  let rest = cps.slice(at + 1);
  if (rest[0] === 0xFE0F) rest = rest.slice(1);      // VS16 now redundant
  return String.fromCodePoint(...cps.slice(0, at + 1), TONES[tone - 1], ...rest);
}

    7
    Measure the width, derive the rows
    
        
    Do not hardcode nine columns and do not ask a media query — the picker can be 340px wide inside a 1440px page, so the only honest source is the element itself. A ResizeObserver reports the content box, the column count is a division, and the row count of every group is a ceil of that. Then flatten the whole picker into one list of rows where a header row is short and an emoji row is tall, and build the cumulative offset array while you are there. Everything after this — the window, the sticky header, the rail sync, the keyboard — reads that one structure.
    
        
    function buildLayout(groups, cols, hdrH, rowH){
  const rows = [], offsets = [], heights = [];
  let y = 0;
  const push = (row, h) => { rows.push(row); offsets.push(y); heights.push(h); y += h; };
  groups.forEach((g, gi) => {
    if (!g.items.length) return;
    push({ type:"header", gi, label:g.name }, hdrH);
    const n = Math.ceil(g.items.length / cols);
    for (let r = 0; r < n; r++)
      push({ type:"cells", gi, from:r * cols, to:Math.min(g.items.length, (r + 1) * cols) }, rowH);
  });
  return { rows, offsets, heights, total:y };
}

new ResizeObserver(([entry]) => {
  const cols = Math.max(6, Math.floor(entry.contentRect.width / CELL));
  if (cols !== state.cols){ state.cols = cols; relayout(); }
}).observe(scroller);

    8
    Binary-search the window, then draw only that
    
        
    With mixed row heights you cannot divide scrollTop by a constant, but the offsets array is strictly increasing, so a binary search finds the first row whose bottom is still below the fold in log time and a short walk finds the last. Add a couple of overscan rows so a fast flick never shows a hole. The canvas keeps its full height so the scrollbar tells the truth, and every visible row is absolutely positioned at its own offset — which means the DOM holds a dozen rows whatever the dataset size.
    
        
    function visibleRange(L, scrollTop, viewportH, overscan){
  const n = L.rows.length, top = scrollTop, bot = scrollTop + viewportH;
  if (!n) return { first:0, last:-1 };
  let lo = 0, hi = n - 1, first = n;
  while (lo <= hi){                                   // first row with bottom > top
    const mid = (lo + hi) >> 1;
    if (L.offsets[mid] + L.heights[mid] > top){ first = mid; hi = mid - 1; }
    else lo = mid + 1;
  }
  if (first === n || L.offsets[first] >= bot) return { first:0, last:-1 };
  let last = first;
  while (last + 1 < n && L.offsets[last + 1] < bot) last++;
  return { first:Math.max(0, first - overscan), last:Math.min(n - 1, last + overscan) };
}

    9
    Frecency — a frequency that forgets
    
        
    A raw counter is wrong within a week: the emoji you used forty times last month permanently outranks the one you have used six times today. Multiply every old score by a half-life decay before adding one for the new pick and the list tracks what you are doing now while still remembering habits. Store four numbers per emoji — the decayed score, the timestamp it was decayed to, a plain count for display, and the last-used time for tie-breaks — and the incremental version is provably identical to summing a decayed weight over the whole event log, which is exactly the property to assert in a test.
    
        
    const HALF_LIFE = 1000 * 60 * 60 * 6;                       // six hours
const decay = (score, dt) => score * Math.pow(0.5, dt / HALF_LIFE);

function frecPick(store, char, now){
  const r = store[char] || { score:0, at:now, count:0, last:0 };
  store[char] = { score:decay(r.score, now - r.at) + 1, at:now,
                  count:r.count + 1, last:now };
}
const frecScore = (store, char, now) =>
  store[char] ? decay(store[char].score, now - store[char].at) : 0;

const frecTop = (store, now, n) => Object.keys(store)
  .map(ch => ({ ch, s:frecScore(store, ch, now), last:store[ch].last }))
  .sort((a, b) => b.s - a.s || b.last - a.last || (a.ch < b.ch ? -1 : 1))
  .slice(0, n);

    A 2-D cursor, roving tabindex, and the caret
    
        
    Keep the cursor as {row, col} over the cells rows only and every arrow is three lines: right wraps to the next row, left wraps back, up and down clamp the column to the shorter row. Because the cursor is state and not focus, the virtual grid can throw its DOM away on every scroll without losing the selection — you simply give the one rendered cell that matches the cursor tabindex="0" and leave the rest at -1. Finally, insert at the caret: grab the live range, delete whatever was selected, drop a text node in and collapse the range after it. Appending to the end is the bug users notice first.
    
        
    function moveCursor(lens, cur, dir){        // lens = cells-per-row
  let { r, c } = cur;
  r = Math.min(r, lens.length - 1); c = Math.min(c, lens[r] - 1);
  if (dir === "right"){ if (++c >= lens[r]){ r = (r + 1) % lens.length; c = 0; } }
  else if (dir === "left"){ if (--c < 0){ r = (r - 1 + lens.length) % lens.length; c = lens[r] - 1; } }
  else if (dir === "down" && r < lens.length - 1){ r++; c = Math.min(c, lens[r] - 1); }
  else if (dir === "up"   && r > 0)            { r--; c = Math.min(c, lens[r] - 1); }
  return { r, c };
}

function insertAtCaret(host, text){
  const sel = window.getSelection();
  let range = (sel.rangeCount && host.contains(sel.anchorNode))
    ? sel.getRangeAt(0)
    : (r => (r.selectNodeContents(host), r.collapse(false), r))(document.createRange());
  range.deleteContents();
  const node = document.createTextNode(text);
  range.insertNode(node);                    // lands where the caret was
  range.setStartAfter(node); range.collapse(true);
  sel.removeAllRanges(); sel.addRange(range);
}
