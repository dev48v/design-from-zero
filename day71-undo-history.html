DESIGNFROMZERO · DAY 71

⏪ Undo history — press Ctrl+Z and the last thing you did comes back. Underneath is not a stack of documents but a stack of inverse patches, and one predicate decides everything you feel about it: whether the keystroke you just made joins the entry on top of the stack or starts a new one. Five clauses answer that. The eight machines here differ by one clause each — and the property every undo test asserts, undo everything, redo the same number of times, the text is back, is satisfied by eight of eight on 100.0% of 700 generated test cases, because on a two-stack machine it is very nearly a tautology. The same round trip asserted on the caret instead of the text separates one of them on 700 of 700. The cap that trims the wrong end of the stack is invisible to three corpora out of four and needs a session longer than the cap — the first operation it gets wrong is a straight line, about six operations per unit of cap. And the clause that looks most essential, that the new edit be contiguous with the run, turned out to be redundant: 0 divergences in 179,243 operations, never once the sole reason for a break, and the input that finally separates it is not a keystroke at all. 6,179,960 assertions on load against a history modelled the other way round — whole-document snapshots and a pointer. Pure vanilla JavaScript, one file, no build step.

Type in the box. Ctrl+Z and Ctrl+Shift+Z work, and so do the buttons. The violet row underneath is the undo stack — one chip per entry, showing what that entry will give back. Watch how many keystrokes collapse into one chip, and where a chip refuses to grow. The panel on the right replays the identical keystrokes through all eight machines.

WHY THE HISTORY IS PATCHES AND THE ORACLE IS SNAPSHOTS

      

        The snapshot model is the obvious one and it is the right oracle precisely because it is the
        wrong implementation: it costs a whole document per entry. Measured on the sessions above,
        then in closed form, where the ratio turns out to be set by the size of the document
        and to have almost nothing to do with how many edits there were.
      

      

      

    


    

      
FIVE SESSIONS, WRITTEN OUT IN FULL

      

      

      

      

      

    


  

  






  

    

      
Undo is not a stack of documents

      

        The first design anybody writes is a list of snapshots. Every time the document changes, push
        a copy; undo is index − 1. It is correct, it is four lines, and it is the
        model this page uses as its oracle — because being obviously correct is exactly
        what an oracle is for. It is also unshippable. A snapshot costs a whole document. Sixty edits
        in a twenty-thousand-character file is 1.2 MB of history for
        2.5 KB of actual change, and the ratio is not a function of how many
        edits there were — it is the length of the document divided by the size of an edit, so
        it gets worse the longer you work.
      

      

        So a real history stores inverse patches. An entry is
        {from, removed, inserted, selBefore, selAfter}: undo splices
        removed back in where inserted is, redo does the reverse. Two
        stacks, one document, and the memory is proportional to what you changed rather than to what
        you were changing it in.
      


      
The whole component is one predicate

      

        Once you have patches, almost nothing is left to decide except one thing, and it is the thing
        every complaint about undo is actually about: when does a new edit join the entry on
        top of the stack instead of starting a new one? Push one entry per keystroke and
        Ctrl+Z becomes a backspace with extra steps. Merge too eagerly and one press eats a
        paragraph. Everything anybody has ever felt about an undo implementation is that predicate.
      

      
Five clauses. A keystroke joins the run only when none of them objects:

      
    
        
  • same kind. Typing joins typing, backspacing joins backspacing, a paste
          joins nothing and nothing joins a paste.
    • 
        
  • the caret has not been moved by hand. Clicking somewhere is a decision;
          it ends the run even if you click back to where you were.
    • 
        
  • the run has not gone quiet. More than the idle window since the last
          keystroke in this entry and the run is over.
    • 
        
  • contiguity. The new edit starts exactly where the run left off —
          which is a different sum for typing, for backspace and for forward delete.
    • 
        
  • no newline. Enter ends the run, so one press never crosses a paragraph.
    • 
      

      

        Everything else — clearing the redo branch, restoring the selection, bounding the stack
        — is a single line each, and each of those single lines is a defect on this page.
      


      
The property everybody tests is nearly a tautology

      

        Search any editor's test suite for its undo tests and you will find this: make some edits,
        press undo k times, press redo k times, assert the text. It is the obvious
        property. It is also the one thing a two-stack machine gets right almost by construction:
        undo pops from one stack and pushes to the other, redo does the
        reverse, so k of one followed by k of the other is a permutation that
        returns to where it started whatever nonsense the entries contain. All eight machines here
        pass it on 100.0% of 700 generated cases. Six of the eight pass it on 100.0% of realistic
        sessions too.
      

      

        What that assertion cannot see: how much one press gave back, where the caret ended up,
        whether the redo button should have been lit, and whether the document it showed you halfway
        through was a document that had ever existed. Those are four different assertions and every
        one of them separates something.
      


      
The branch is where undo stops being a stack

      

        Undo three times and then type. The three entries you undid are now unreachable — you
        have moved onto a different branch of the document's history and the old one is gone. One
        line clears the redo stack when a new edit arrives. Leave that line out and the entries stay,
        describing a document that no longer exists, and the next Ctrl+Y splices them into the
        document you have now. The result is not a stale state. It is a state that no edit ever
        produced: type the quick brown fox, undo it, type hello, press
        redo, and the machine hands you the quick brown foxhello.
      

      

        And you do not have to press redo to see it. The moment you branch, the machine believes it
        has something to redo, so the button lights up and the menu item enables. That single boolean
        disagrees with the truth on three quarters of the operations in a realistic session —
        far earlier and far more reliably than any comparison of the text.
      


      
The caret is half the feature

      

        An entry stores two selections, not one: where you were before the edit and where you were
        after. Undo restores the first, redo restores the second, and the reason is that undo is
        supposed to take you to what changed. Restore the text and leave the caret alone and
        every text assertion in your suite still passes — on the corpus a test suite generates,
        on 100.0% of cases — because the caret is not in the assertion. Then somebody types one
        more character, it lands one position off, and you have a text bug two operations away from
        its cause and in a different part of the file. It shows up as
        hello ?world where it should have been hello? world.
      


      
The clause that turned out to be redundant

      

        Contiguity is the clause that feels like the heart of the rule, and on this page it does
        nothing. Counting all the reasons for every refusal rather than just the first one:
        across four corpora and 179,243 operations, the contiguity check was a reason thousands of
        times and the sole reason zero times. A machine with the clause deleted
        diverges on exactly nothing, anywhere.
      

      

        The reason is structural rather than lucky. If the caret is where the last edit left it, the
        next keystroke is contiguous by construction; and the only things that can move the caret
        — a click, an arrow key, an undo, a paste — have already tripped a different
        clause. So for a single person at a keyboard, contiguity is implied by the other four.
      

      

        It stops being implied the moment a change to the document does not come from that keyboard.
        A collaborator's patch, a find-and-replace, an autocompletion, a language server's formatting
        pass: those move text under the caret without any of the other four clauses noticing. Type
        abc, let a collaborator insert XY at the top, type d,
        press undo once. With the clause you get XYabc. Without it, one press returns
        cd — it deleted the collaborator's text and half of yours. The clause is
        not there for your keystrokes. It is there for everybody else's.
      


      
Bounding the stack

      

        History has to be capped. Capping it is where shift() and pop()
        differ by two characters and by everything: one drops the oldest entry, the other drops the
        entry you just made, and the second means the newest edit is not undoable — press
        Ctrl+Z and you jump back past the thing you were trying to take back. It is completely
        invisible until a session produces more entries than the cap, which is why three of the four
        corpora on this page never see it and the test-suite corpus never could: a generated test
        case makes about one entry.
      


      
Which corpus can see what

      

        Day 70's lesson was that a realistic corpus is not a concentrated one, and a budget is only
        visible to a corpus that spends it in one place. This page inverts it. Here the blind corpus
        is the generated one, and it is blind for four separate reasons: it never branches,
        so a stale redo stack is unreachable; every operation is one clock tick apart, so a machine
        with no idle window behaves identically to one that has it; the caret never moves on its own;
        and a test case is far too short to reach a cap. Four of the seven defects need a corpus that
        has a clock, a caret, a branch and a length, and a generated fixture has none of the four.
      

    

  






  

    

      
🔨 How it is built


      
1. One block of pure functions and no DOM

      

        Everything between ENGINE:BEGIN and ENGINE:END is pure. The machine
        is newHist, pushEdit, doUndo, doRedo; the
        predicate is canMerge; the oracle is truthNew,
        truthEdit, truthUndo, truthRedo; the streams are
        genOps. The verifier lifts that block out of the page by regex, refuses it if it
        mentions document, and runs it under node against assertions written separately.
      


      
2. Two models that do not share a line

      

        The implementation keeps inverse patches on two stacks and edits a string with
        slice. The oracle keeps whole-document snapshots in an array with an
        index, holds each document as an array of characters, and edits with
        Array.prototype.splice. The merge decision is the one piece of logic they both
        need, so it is written twice in two different shapes: the implementation is a chain of early
        returns that answers yes or no, and the oracle collects a list of reasons to break
        and merges when the list is empty. That second shape is what made the redundant clause
        visible — a boolean cannot tell you which clause was load-bearing.
      


      
3. Eight machines, one clause each

      

        The document, the op streams, the clock and the assertions are shared. Each machine changes
        exactly one thing: coalescing off entirely (every), the clock without the
        position or the caret (timeonly), contiguity without the clock
        (nogap), the missing redo.length = 0 (noclear), undo
        that restores the text and not the selection (doconly), pop() where
        the cap wanted shift() (capnew), and the contiguity clause deleted
        (nocontig). Every one of them is a thing that ships.
      


      
4. Four op streams, because one cannot see anything

      

        Positions in an op are fractions of the document rather than offsets, so the
        same stream is legal in whatever document a machine is holding however far the eight have
        drifted apart — which is also what happens to a person, whose next keystroke lands
        wherever their editor left the caret. a test suite is a generated case: a few edits,
        undo them, redo them, assert. a real session is somebody writing, with a
        heavy-tailed gap distribution, typo bursts, clicks, pastes and undo used the way undo is used
        — mostly to take a run back and write something different instead. the seams
        aims at the five clauses: pauses landing exactly on the window, caret moves that come
        straight back, an edit after every undo. a whole day is the same as a real session
        and fourteen hundred operations long, which is the only one of the four that outlives the cap.
      


      
5. The oracle that could not be the oracle

      

        The honest way to answer "what is the document now" is to replay the entire operation stream
        from empty after every operation. That is O(n²) in operations and O(n·m) in
        characters and it would take the fuzz off a cliff, so the shipped oracle carries an index
        instead and the replay is kept as a bounded spot check — 
        assertions over  replayed steps, 0 disagreements. The snapshot array
        is itself the O(n·m) object, which is exactly why it is a good oracle and a bad
        implementation.
      


      
6. What the tests pin

      
    
        
  • The document, the selection, canUndo and canRedo against the
          snapshot oracle after every operation, for all eight machines, in all four corpora.
    • 
        
  • The undo/redo round trip on the text and on the caret at the end of every session.
    • 
        
  • Every document a machine displays against the set of every document any edit produced.
    • 
        
  • Entry counts, characters per press and the worst single press with no undo in the stream,
          so the granularity comparison is like for like.
    • 
        
  • The idle window swept over an order of magnitude, and the cap swept over five values.
    • 
        
  • The same seed gives the same session; a different seed does not.
    • 
      


      
7. What contradicted the first draft

      
    
        
  • The plan was that the realistic corpus would be the blind one, as on Day 70. It is the
          opposite here: the blind corpus is the one a test suite generates, and it is blind
          four times over — no branches, no clock, no caret movement, no length.
    • 
        
  • The round trip was drafted as a property that some broken versions would pass.
          It is passed by all eight on the generated corpus, and the reason is
          structural rather than a coincidence of these particular defects: on two stacks, k
          pops one way followed by k the other way is a permutation that has to return.
    • 
        
  • Contiguity was drafted as the core of the merge rule and is dead code for a single person
          at a keyboard: never the sole reason for a break in 179,243 operations, and 0 divergences
          with it deleted. The input that separates it had to be built by hand and is not a keystroke.
    • 
        
  • The idle window was expected to be delicate. It is not: moving it from 400 ms to
          700 ms — a 75% change — moves what a press gives back by
          . What it is not is a word boundary; at 500 ms a
          press returns  words, and you would have to come down to around
          280 ms to get one.
    • 
        
  • The redo-stack defect was drafted as the one the realistic corpus would struggle with,
          on the grounds that people rarely press redo after branching. The document comparison does
          struggle. canRedo does not: it is wrong on
           of operations and catches it in
           of realistic sessions, and it is one boolean.
