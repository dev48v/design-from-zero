DESIGNFROMZERO · DAY 72

⇅ Multi-key table sort — click a column header and the rows rearrange. The part that decides whether the table is right is not the comparison, it is what happens to the rows the comparison cannot separate: a table sort has to be a total order or the same rows come back arranged differently every time the query does. The seven implementations here differ by one clause each, and on a hand-written test fixture — a few rows, every value different, nothing blank — all seven produce the identical order on 100.0% of 800 cases and on every one of the six sort specs, so that fixture cannot tell a correct sort from any of the six broken ones. The property every table test does assert, the column you clicked is in order, is satisfied on 100.0% of every corpus by four of the seven — one of which gets 86.7% of real boards wrong. And what blinds the fixture is not its realism but its row count: the four defects it can ever see appear at 6, 10, 21 and 21 rows, where 21 is lcm(5,4) + 1, the first row count at which two of its rows can tie on both keys at all — while the other two are invisible at every row count, forever, for a reason that is not about size. 4,340,301 assertions on load against an oracle that never compares two rows. Pure vanilla JavaScript, one file, no build step.

Click a column header. The first click makes it the primary key, clicking it again flips the direction, and shift-click appends a key instead of replacing one. The violet chips are the sort spec; the grey one at the end is the tie-break that makes the order total. Then press run the query again: the rows are handed to the sort in a different physical order, exactly as a second database query would hand them over, and anything that moves is a row your table cannot keep still.

AND THE TWO ORDERS BOTH CALLED NATURAL SORT

        

          The machine walks digit runs and compares each run against the run facing it. The oracle
          zero-pads the digit runs and compares one flat string. Both are the thing people mean by
          natural sort and they are not the same order — which matters, because if
          they disagreed anywhere in the corpus the oracle would not be an oracle.

A table sort is not a comparison. It is a total order.

      

        Clicking a column header does not sort by that column. It builds a sort spec —
        an ordered list of {key, direction} — and hands the whole list to a
        comparator that walks the keys until one of them separates the two rows. That much everybody
        writes correctly on the first try. The part that decides whether the table is right is what
        happens when the walk runs out of keys: two rows the spec cannot separate, and no answer.
      

      

        Return 0 there and the comparator is a total preorder: valid, antisymmetric,
        transitive, and it will pass every axiom check you can point at it. What it is not is a
        total order, and the difference is the whole component. A total preorder
        says these two rows are equivalent; the sort is then free to put them in either
        arrangement, and which arrangement you get depends on the order the rows physically arrived
        in — which is to say, on the query plan, the buffer pool, and whatever the database
        felt like doing that afternoon.
      

      

        On one screen that is invisible. Across two it is a bug report. Add one clause —
        then by id — and no two distinct rows can ever tie again, so the sort is a
        function of the set of rows rather than of the order they turned up in. That clause
        is the last one in the comparator, the one that never fires on anybody's test data, and it is
        the one everyone deletes.
      


      
The fixture cannot see any of it

      

        Beside the correct machine on this page sit six implementations, each differing by one
        clause. On a hand-written test fixture — a few rows, every column deliberately
        different, nothing blank, every number one digit wide — all seven produce the
        identical order, on 100.0% of 800 fixtures and on every one of the
        six sort specs. That is not a near miss. Across seven implementations and six specs the
        fixture records zero disagreements of any kind.
      

      

        The interesting part is why, because the usual explanation — the fixture is
        not realistic enough — is wrong here, and measurably so. Hold the generator to exactly
        its own rules and just add rows:
      

      
    
        
  • 6 rows. First key only starts failing, because the status
          column has five values and six rows is the first count at which two rows can share one.
    • 
        
  • 10 rows. Sort then reverse starts failing: the points column
          cycles through nine values.
    • 
        
  • 21 rows. Both tie-break defects start failing at once, and 21 is
          lcm(5,4) + 1 — status cycles every 5 rows and priority every 4,
          so the first pair of fixture rows that agree on both keys is exactly 20 apart.
    • 
      

      

        Three thresholds, all arithmetic, none of them about realism. And the remaining two defects
        are invisible at every row count, forever, for a reason that is not about size at
        all: the fixture has no blank cell for blank is zero to coerce, and its numeric
        columns are all one digit wide, where a string comparison and a numeric comparison are the
        same order. No amount of rows fixes a column that has no gaps in it.
      


      
The property everybody asserts

      

        Search any table component's tests and you will find one assertion: click the header, then
        walk the rendered rows and check the column is in order. It is the obvious property. It is
        also satisfied on 100.0% of every corpus by four of the seven
        implementations here — the correct one, both tie-break defects, and first key
        only, which is exactly right on 13.3% of real boards.
      

      

        That last one deserves a moment. It reads the first key of the spec, sorts by it, appends the
        tie-break and throws the other four keys away. The column you clicked comes out in perfect
        order. Every row you can see is where you would expect. And it is a different arrangement
        from the correct one on 86.7% of real boards, putting 789
        rows per 1,000 somewhere other than where they belong. The property cannot see it because the
        property only reads the column it was told about, and that column is the one thing this
        implementation gets right.
      


      
Five properties, and the two that look identical

      

        So write more properties. Is the whole spec in order, not just the first key.
        Does a second query give the same screen. Does asc, desc, asc come back to where
        it started. Do two pages of twenty contain forty distinct rows. Each one catches
        something the others miss and none of them is a superset of another, which is the usual
        finding. The unusual one is what separates the two implementations that behave most alike.
      

      

        No tie-break and unstable sort score within three points of each other on
        every column but one: 43.3% and 43.7% on the second query, 63.7% and 63.0% on pagination,
        42.0% and 44.7% exactly right. The round trip splits them cleanly — 100.0% for
        the missing tie-break, 43.3% for the unstable sort — and the reason is
        structural rather than lucky. Flipping the first key's direction does not change which
        rows are tied; it is the same set of rows either way. So a stable sort returns a tied group in
        the order it found it in both directions, and the round trip comes back exactly. The round
        trip is blind to a missing tie-break by construction. What it sees is an actual instability,
        and nothing else on the page sees that alone.
      

      

        The other reading of that grid is that the five properties rank in almost exactly the reverse
        of how often they get written. Is the first key in order is the assertion that
        exists in every suite, and on a real board it is 100.0% for three of the six
        defects — it cannot see a missing tie-break, an unstable sort, or a spec with four
        fifths of its keys thrown away. Do two pages of twenty hold forty distinct rows is
        the assertion almost nobody writes, and on a real board it is the only one
        of the five that is under 100.0% for all six. It is not free, either: on the seams corpus,
        where the whole table fits inside two pages, the same assertion falls back to catching only
        the two implementations that can duplicate a row. The property is doing its work because the
        table is bigger than the screen, which is the condition under which the bug matters anyway.
      


      
Pagination is where it stops being cosmetic

      

        Twenty rows come back from one query and twenty more from the next. If the order is not
        total, nothing decides which of two tied rows page 1 kept and which one page 2 thought it
        still owed you — so one row is printed twice and another is never printed at all. Over
        300 boards the missing tie-break duplicates 279 rows and loses
        465.
      

      

        The four defects that cannot duplicate a row are the ones worth thinking about.
        Sort then reverse, first key only, numbers as text and blank
        is zero are all perfectly deterministic total orders: the same rows always come back the
        same way, so the two pages are always consistent with each other. They just quietly hand you
        the wrong forty rows — 682, 551, 241
        and 941 rows respectively that belonged on the first two pages and were never
        shown. Determinism is not correctness. It is only the absence of the duplicate, which is the
        one symptom anybody files a ticket about.
      


      
Which clause is doing the work — asked two ways that disagree

      

        There is a tidy way to find dead code in a comparator: for every neighbouring pair in the
        finished order, record which clause was the first to separate them. A clause that separates
        nothing is doing nothing.
      

      

        Run it on the fixture with status, priority and it reports that
        status decides 100.0% of all 597 pairs and that
        priority and the tie-break decide nothing at all. By this test
        two of the three clauses are dead code and both should go. Run the same spec on a real board
        and status decides 5.6%, priority
        16.9%, and the tie-break the fixture called dead does 77.5%
        of the work.
      

      

        Then there is the direct version: delete the clause, sort again, count what changed. On the
        five-key board spec the two questions come apart in a way that is worth staring at. Deleting
        status, the loudest clause there is, moves 981 rows per 1,000
        and leaves the second-query column at 100.0% — a completely different
        screen that is nonetheless perfectly stable. Deleting the tie-break instead moves
        11.7 rows per 1,000 and leaves 70.0% of screens
        byte-identical, which in a review reads as rounding — while the second-query column
        falls to 69.3%. A missing key is loud and stable. A missing tie-break is
        quiet and not, and only one of the two columns can tell you so.
      


      
The clause behind the clause

      

        Underneath the tie-break there is one more. The text comparison folds case and accents so
        that Zoe, Zöe and zoe group together, and then falls
        back to the exact form of the string so that two values that fold together still get
        an order. On a real board that fallback is genuinely unreachable: 0 pairs out
        of 10,258 where it would have been the deciding clause. Delete it and nothing changes,
        anywhere, with or without the tie-break.
      

      

        On the seams corpus, where names differ only by case and accent, it would decide
        173 pairs — and deleting it still leaves 80.7%
        of screens identical, because the id tie-break quietly absorbs the pairs it used to handle.
        Take both away and stability collapses to 52.0%. Two clauses, each of which
        measures as dead code for exactly as long as the other one is there. That is the failure mode
        of clause-level coverage as a design tool, and it is the reason the tie-break survives in
        correct code only because somebody refused to delete something they could not justify.
      


      
Checking the comparator finds none of it

      

        A comparator has to be antisymmetric, reflexive and transitive or the sort is entitled to
        return anything at all, and checking those three is the one piece of diligence this component
        has a name for. All seven implementations pass all three, with zero violations on every
        triple tested. Three of the six defects are impeccable comparators answering a question
        nobody asked. One is a valid preorder that returns 0 for two rows that are not the same row.
        And two are not comparator defects at all — they share their comparator with the
        correct implementation and differ in what happens after it returns.
      

      

        The check that does mean something is exhaustive and does no sorting: enumerate every
        permutation of a small table and keep the ones that are non-decreasing. A total order leaves
        exactly one, and it did, in 100.0% of 600 tables — each of which is the
        arrangement the implementation produced. That is what total means, verified without a sort
        algorithm anywhere in the room.
      


      
Which corpus can see what

      

        Day 69's lesson was that a generated corpus and a real one score identically on clean data
        and part company on messy data. Day 70's was that a realistic corpus is not a
        concentrated one. This page adds a third: the fixture's blindness here is
        arithmetic, not statistical. Three of its five thresholds are exactly one more than
        the size of a value pool, and the two defects it never sees are unreachable because the
        fixture's columns have no blanks and no digit-width variation — two structural
        properties, not two unlucky draws. You can compute in advance which defects a fixture is
        capable of finding. That is a more useful thing to know about a test corpus than whether it
        looks like production.
      

    

  






  

    

      
🔨 How it is built


      
1. One block of pure functions and no DOM

      

        Everything between ENGINE:BEGIN and ENGINE:END is pure. The
        comparator is makeCmp, built from a spec and four option flags; the seven
        machines are IMPLS; the corpora are genFixture,
        genSeeded, genBoard and genSeams; the studies are
        fuzz, sizeSweep, specSweep, clauseStudy,
        deleteStudy, foldStudy, toggleStudy,
        axioms and permStudy. The verifier lifts that block out of the page
        with a regex, refuses it if it mentions document, and runs it under node against
        oracles written separately from it.
      


      
2. An oracle that never compares two rows

      

        The machine dispatches on column type at every comparison and walks the spec key by key. The
        oracle does none of that. It collects each column's distinct values once, puts them
        in order once, and turns every row into a vector of small integers; the
        answer is the lexicographic order on those vectors, produced by a bottom-up merge sort that
        never touches Array.prototype.sort. Descending flips the sign of the
        rank, which is also why a missing value — pinned at a constant and never
        flipped — sorts last in both directions without anything special being written for it.
      

      

        Two rows are therefore compared as integers, once per case, by code that has no idea what a
        status or a due date is. A second oracle, a quadratic selection sort taking the first minimum
        each time, runs on every case of 24 rows or fewer as a check that the fast oracle is the same
        oracle. And a third check does no sorting at all: enumerate every permutation of a
        three-to-five-row table, keep the ones that are non-decreasing, and assert exactly one
        survives.
      


      
3. Two orders both called natural sort, and why it matters

      

        natCmp cuts each string into runs of digits and runs of everything else and
        compares run against run, numbers as numbers. The oracle's encVal zero-pads the
        digit runs and compares one flat string. Both of those are what people mean by natural sort
        and they are not the same order: they part company exactly where a digit run
        faces a character below "0". On strings built to break them,
        73 of 20,000 pairs disagree.
      

      

        That is a problem only if it happens on the data. So every distinct pair of every text column
        of every case is checked both ways — 160,919 pairs across the four
        corpora, 0 disagreements. The oracle is allowed to be the oracle on this
        corpus and nowhere else, and the page says so with a number rather than a hope.
      


      
4. Seven machines, one clause each

      

        The rows, the specs, the oracle and the assertions are shared. Each machine changes exactly
        one thing: the final id clause removed (notiebreak), a hand-rolled
        median-of-three quicksort in place of the stable sort (unstable), descending
        implemented as ascending followed by .reverse() (reversed), the
        spec truncated to its first key (firstkey), numeric columns compared in their
        string form (numtext), and a missing value coerced to zero instead of pinned
        last (nullzero). Every one of them is a thing that ships, and
        unstable is not a straw man: Array.prototype.sort was itself
        unstable in V8 until 2018 and plenty of table code still carries its own sort.
      


      
5. Four corpora and six specs, because one of each sees nothing

      

        A test fixture is what almost every sort test is built on: three to five rows, every
        column deliberately different, nothing missing, every number one digit wide. A seeded
        table is the same schema handed to a random generator, so ties happen where the pools
        are small and blanks happen at their declared rate. A real board is skewed —
        two statuses hold most of the work, a couple of people hold most of the tickets, titles repeat
        because the same bug gets filed twice, and everything was touched on one of three days because
        somebody ran a bulk update. The seams aims at the clauses: a first key with one value
        in it, a column that is entirely missing, names that differ only under folding, numbers whose
        digit widths cross.
      

      

        The six specs matter as much as the corpora, and the grid says why. Sort then reverse
        is 0.0% on the two all-ascending specs and 100.0% on the three whose first key descends.
        First key only is 0.0% on exactly one spec — the single-key one, where there
        is no rest of the spec to discard. Numbers as text needs a numeric column whose
        values differ in width and is 0.0% on the four specs that have none. Blank is zero
        needs a nullable key and is 0.0% on the three specs built only from columns that cannot be
        blank. Every defect on this page is 0.0% under some spec and 100.0% under another, on the
        same corpus, for structural reasons that are written out under the grid.
      


      
6. What the assertions pin

      
    
        
  • The exact order, row for row, against the oracle — and against the oracle run again
          on the same rows shuffled, so the oracle is proved to be a function of the set before it is
          used to judge anything.
    • 
        
  • Five weaker properties per case: first key in order, whole spec in order, same screen
          after a second query, asc/desc/asc returns, two pages of twenty hold forty distinct rows.
    • 
        
  • Every output is a permutation of the input, which is the assertion that catches a sort
          that drops or duplicates a row outright.
    • 
        
  • Antisymmetry, reflexivity and transitivity for all seven comparators, counting
          violations rather than passes.
    • 
        
  • Both natural orders against each other, on adversarial strings and on the corpus.
    • 
        
  • The clause-counting study and the clause-deletion study, which are the same question and
          do not give the same answer.

7. What contradicted the first draft

      
    
        
  • The plan was to say the fixture is blind because it is not realistic. It is blind because
          of its row count and its pool sizes, and the thresholds are arithmetic:
          6 = 5 + 1, 10 = 9 + 1, and 21 = lcm(5,4) + 1 for both tie-break defects at once. The draft
          said three defects appear at 6, 10 and 21; it is four, two of them arriving together at 21
          because that is the first row count at which two fixture rows agree on both keys.
    • 
        
  • Two of the six are unreachable by that fixture at any size, which is a different
          kind of blindness and does not get better with more rows: there is no blank cell to coerce
          and no numeric column wide enough for a string compare to differ from a numeric one.
    • 
        
  • The asc/desc/asc round trip was drafted as a weak property that would catch nothing much.
          It is the only one of the five that separates the unstable sort from the missing
          tie-break, and the reason is structural: flipping the first key's direction does not change
          which rows are tied, so a stable sort hands a tied group back in the order it found it
          either way. The round trip is blind to a missing tie-break by construction and sees an
          actual instability alone.
    • 
        
  • Counting which clause decides a pair and deleting that clause were drafted as two views of
          one number. On the five-key board they invert: the clause whose deletion changes the most
          rows leaves the result perfectly stable, and the clause whose deletion changes 11.7 rows per
          1,000 is the one that destroys stability. Neither number can be derived from the other.
    • 
        
  • The five properties were expected to rank roughly in order of effort. They rank in the
          reverse of how often they get written: the universal one, is the first key in order,
          is 100.0% for three of the six defects on a real board, and the one almost nobody writes,
          do two pages of twenty hold forty distinct rows, is the only one of the five under
          100.0% for all six — and only while the table is larger than two pages, which the
          seams corpus is not.
    • 
        
  • The exact-form fallback under the fold was expected to be dead code and it is — but
          only while the tie-break is there. Remove both and the seams corpus loses stability on
          nearly half its boards, which means neither clause can be justified by measuring it alone.
