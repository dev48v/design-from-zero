▸ Toggle blocks — the component people build as a nested <details> and then cannot make outline. The document here is a flat array of { id, text, depth, open }, never a tree, because every operation you actually want — Tab to indent, Shift+Tab to outdent, drag a block and take its children with it, collapse a parent and hide a whole subtree — is a contiguous range in a flat list and a graph rewrite in a tree. Visibility is derived, never stored: a block is hidden iff any ancestor is collapsed, which is one backward scan. Indent is legal only if it does not skip a level, so depth can never go invalid. Drag-and-drop moves the whole subtree and refuses to drop a block inside itself. The flat model is fuzz-tested in Node against a real tree built with parent pointers — 2 representations, 0 shared code.

Why not a tree, and why not <details>


      
The obvious model for nested toggles is a tree of nodes with children arrays,
      rendered as nested <details> elements. It works right up until you want the
      thing that makes an outliner an outliner: Tab to indent the block you are typing in.


      
In a tree, indenting is a graph rewrite. Detach the node from its parent, find the previous
      sibling, append to its children, and re-parent every descendant pointer. Outdent is the
      same surgery backwards, plus the fiddly part nobody remembers first time — the blocks
      after you must become your children. Every one of those steps can leave the tree
      inconsistent halfway through.


      

        
The same document, flat:

        
[ { id:1, text:"Trip",       depth:0, open:true  },
  { id:2, text:"Flights",    depth:1, open:true  },
  { id:3, text:"Outbound",   depth:2, open:true  },
  { id:4, text:"Hotels",     depth:1, open:false },
  { id:5, text:"Riverside",  depth:2, open:true  } ]

        
Indent block 4 is now b[3].depth++.
        One integer. It cannot leave anything dangling because there are no pointers to dangle.

      


      
The one rule that keeps a flat list a tree

      
A flat array with arbitrary depths is not a tree — [0, 2] means nothing, because
      block two claims a grandparent that does not exist. So exactly one invariant is enforced:

      

        depth[i] ≤ depth[i−1] + 1, and depth[0] === 0
      

      
Indent is refused when it would break that, which is why the Tab key sometimes does
      nothing — the first block of a level has nothing to indent under. That is not a missing feature;
      it is the invariant holding. The panel re-checks the whole sequence after every edit.


      
A subtree is a range, not a traversal

      
Everything nested under block i is the run of blocks after it with a strictly
      greater depth — and because depth can only rise one step at a time, that run is
      contiguous. So:

      
function subtreeEnd(b, i){
  let j = i + 1;
  while (j < b.length && b[j].depth > b[i].depth) j++;
  return j;                       // subtree is [i, j)
}

      
Collapse hides [i+1, j). Delete splices [i, j). Drag moves
      [i, j). One function, four features — and it is a scan, not a recursion, so there
      is no stack depth to worry about on a big document.


      
Visibility is derived, never stored

      
The tempting bug is to store a hidden flag and update it when a parent toggles.
      Then collapse a parent, collapse a child inside it, expand the parent, and watch the child come
      back expanded — because two sources of truth drifted.

      
function visible(b, i){
  let need = b[i].depth;
  for (let k = i - 1; k >= 0 && need > 0; k--){
    if (b[k].depth < need){       // this is an ancestor
      if (!b[k].open) return false;
      need = b[k].depth;
    }
  }
  return true;
}

      
One backward scan, no stored state, no possible drift. A block is hidden if and only if some
      ancestor is closed — which is the definition, expressed directly.


      
Dragging, and the move that must be refused

      
Moving a block takes its subtree with it. The interesting case is the illegal one: dropping a
      block inside its own subtree. In a tree that produces a cycle and an infinite render.
      In the flat model it is an index comparison — the target must not lie in [i, j) —
      so the bug that hangs the browser becomes an if.


      
What this is not

      
This is not an accordion. An accordion is a flat one-of-N picker where opening one panel
      often closes the others, and nesting is not part of the idea. A toggle block is a
      document primitive: arbitrarily deep, independently open, reorderable, and the thing
      you are typing into. The shared visual — a caret and some hidden content — hides two completely
      different data models.


    

  







  

    


      
🔨 Build it yourself

      
The whole engine is pure functions over an array. Nothing below touches the DOM, which is
      what makes it testable — and it is tested, against a different representation entirely.


      
1. The document

      
let nextId = 1;
const block = (text, depth) => ({ id: nextId++, text, depth, open: true });

      
Four fields. No parent, no children, no hidden. Everything else is computed.


      
2. The invariant, checked not assumed

      
function validDepths(b){
  if (b.length && b[0].depth !== 0) return false;
  for (let i = 1; i < b.length; i++)
    if (b[i].depth > b[i-1].depth + 1 || b[i].depth < 0) return false;
  return true;
}


      
3. Subtree range — the function everything else is built on

      
function subtreeEnd(b, i){
  let j = i + 1;
  while (j < b.length && b[j].depth > b[i].depth) j++;
  return j;
}
const hasChildren = (b, i) => subtreeEnd(b, i) > i + 1;


      
4. Indent and outdent

      
Indent moves one block and drags its subtree along by the same amount, so relative depths
      inside the subtree are untouched. Outdent must also adopt the following siblings, or they end
      up orphaned at a depth that breaks the invariant.

      
function indent(b, i){
  if (i === 0) return false;                       // nothing above to nest under
  if (b[i].depth > b[i-1].depth) return false;     // already as deep as legal
  const j = subtreeEnd(b, i);
  for (let k = i; k < j; k++) b[k].depth++;        // subtree moves as one
  return true;
}

function outdent(b, i){
  if (b[i].depth === 0) return false;
  const j = subtreeEnd(b, i);
  // blocks after my subtree at my old depth become my children
  let k = j;
  while (k < b.length && b[k].depth > b[i].depth - 1) k++;
  for (let x = j; x < k; x++) { /* they keep their depth, I rise past them */ }
  for (let x = i; x < j; x++) b[x].depth--;
  return true;
}

6. Move a subtree, and refuse the cycle

      
function move(b, i, target){
  const j = subtreeEnd(b, i);
  if (target >= i && target < j) return false;      // dropping inside myself
  const snapshot = b.map(x => ({ ...x }));
  const cut = b.splice(i, j - i);
  const at  = target > i ? target - cut.length : target;
  b.splice(at, 0, ...cut);
  // re-seat the moved subtree at a legal depth for its new neighbourhood
  const base = at === 0 ? 0 : Math.min(cut[0].depth, b[at-1].depth + 1);
  const shift = base - cut[0].depth;
  for (let k = at; k < at + cut.length; k++) b[k].depth += shift;

  // ...but that only fixes what comes BEFORE the run. If the drop landed inside
  // someone else's subtree, the blocks AFTER it are now orphaned at an illegal
  // depth. Validate and roll back rather than re-parent them behind the user's back.
  if (!validDepths(b)){ b.length = 0; b.push(...snapshot); return false; }
  return true;
}


      
7. Prove it against a real tree

      
The flat model is convenient, which is exactly why it deserves suspicion. So build the same
      document a second way — actual nodes with parent pointers and children arrays — apply the same
      random operations to both, and compare the flattened outlines after every single step. The two
      share no code, so they cannot agree for the wrong reason.

      
for (let step = 0; step < 500; step++){
  const op = pick(["indent","outdent","insert","delete","move","toggle"]);
  applyToFlat(flat, op, args);
  applyToTree(tree, op, args);
  assertEqual(renderFlat(flat), renderTree(tree));   // text + depth, in order
}

      
Press the button on the TRY IT tab to run it. When a fuzz test disagrees, it is almost always
      the test model that is wrong first — which is itself useful, because it means you have
      two specifications of the same behaviour and one of them is under-thought.
