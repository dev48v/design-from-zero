The Browser's Own "Open the File" Default Is Killed With preventDefault. No Library.

Drag files onto the box and it lights up; drop them and they upload — or click it to browse. Same zone, two ways in.

A file dropzone is the thing you meet everywhere you upload something: a Gmail attachment, a profile photo, a CSV import, a Figma asset. The whole trick is that a browser already knows what to do when you drop a file on a page — it opens the file and throws your app away — so step one is telling it "no, I'll handle this" with preventDefault on the drag events. Then it becomes friendly: dragenter/dragover highlight the zone so you know it will accept the drop, drop reads e.dataTransfer.files, and because dropping is awkward on a laptop the same box is clickable and forwards to a hidden <input type="file">. Every file is validated for type and size (and told why if it's rejected), listed with its name and size, given a progress bar and a ✕ to remove it, and images get a thumbnail read straight from the file with FileReader — no upload needed to preview. Try it: drag a few files in (or click), watch the read-out on the right update live.

This panel is a pure function of the dropzone's state. Drag a file over the box and dragging over flips to yes; drop it and it joins accepted with a live progress bar, or bounces to rejected with a reason if it's the wrong type or over 5 MB. Everything you see — the list, the bars, the counts — is rendered from one array of file objects.

Attach a file to an email, set a profile picture, import a spreadsheet, upload a design asset — the same object every time: a zone that accepts files two ways and gives instant feedback. The layout is trivial — a dashed box and a list. The craft is the behaviour: stopping the browser's default so a drop doesn't navigate away, highlighting on drag so it's obvious the drop will land, reading the real DataTransfer.files, a click-to-browse fallback through a hidden input, honest validation with a reason, a per-file progress UI, and FileReader thumbnails so images preview before they ever leave the page. Get those right and you have a real uploader, no dependency needed.

🔨 Build it yourself

    
A dropzone is a box plus a hidden file input, and the behaviour is everything: stop the browser from opening a dropped file with preventDefault, highlight the box on dragenter/dragover, read the files out of e.dataTransfer.files on drop, add a click-to-browse path through a hidden <input type="file">, validate each file's type and size, then render a list with a progress bar, a ✕ to remove, and a FileReader thumbnail for images. We build all of it from scratch, one piece at a time, no framework and no dependencies.

    
    
      
  1. 
        
    1
    The markup — a box and a hidden file input
    
        
    Two elements do all the work. A visible .dz-area is the drop target and the click target; alongside it sits a real <input type="file" multiple> that we hide (visually, not with display:none, so it still works) and drive programmatically. The accept attribute hints the OS file picker at what to show. A small but important CSS line: set pointer-events:none on the box's children so a drag or click never gets intercepted by the icon or the text inside — the events always resolve to the box itself.
    
        
    <div class="dz-area" id="zone" tabindex="0" role="button"
     aria-label="Drop files here or press Enter to browse">
  <div class="dz-cloud">⇪</div>
  <div>Drag & drop files here, or <b>click to browse</b></div>
</div>
<input type="file" id="picker" multiple
       accept="image/*,application/pdf" class="sr-only">
<div id="list"></div>   <!-- file rows render here -->

/* CSS: .dz-area * { pointer-events:none } — kids never steal the drop */
    
      
    2. 
      
  2. 
        
    2
    Stop the browser opening the file — preventDefault
    
        
    This is the one line without which nothing else matters. A browser's default reaction to a file dropped anywhere on the page is to navigate to it — your app vanishes and you're staring at a raw JPEG. To claim the drop you must call e.preventDefault() on both dragover and drop (dragover too, or the drop is never even offered to you). Do it on the zone, and also on the whole window, so a near-miss that lands just outside the box doesn't blow the page away either.
    
        
    const zone = document.getElementById("zone");

// on the zone: claim every drag phase
["dragenter","dragover","dragleave","drop"].forEach(evt =>
  zone.addEventListener(evt, e => { e.preventDefault(); e.stopPropagation(); })
);

// safety net: a drop OUTSIDE the zone must not navigate away either
["dragover","drop"].forEach(evt =>
  window.addEventListener(evt, e => e.preventDefault())
);
    
      
    3. 
      
  3. 
        
    3
    Light it up — highlight on drag, and a depth counter
    
        
    Feedback is what makes a dropzone feel alive: while a drag hovers, the box should glow so the user knows the drop will be accepted. Add a class on dragenter/dragover and remove it on dragleave/drop. The catch: dragleave also fires every time the pointer crosses from the box onto a child element, so a naive listener flickers. The fix is a small depth counter — increment on enter, decrement on leave, and only un-highlight when it hits zero (we set pointer-events:none on children in step 1, which also helps).
    
        
    let depth = 0;
zone.addEventListener("dragenter", () => {
  depth++; zone.classList.add("dz-over");
});
zone.addEventListener("dragover",  () => zone.classList.add("dz-over"));
zone.addEventListener("dragleave", () => {
  depth--;                        // crossing onto a child fires dragleave too
  if (depth <= 0) { depth = 0; zone.classList.remove("dz-over"); }
});
// (drop resets depth = 0 and removes the class — next step)
    
      
    4. 
      
  4. 
        
    4
    Read the drop — e.dataTransfer.files
    
        
    The payload of a drop lives on the event: e.dataTransfer.files, a FileList of real File objects (each with .name, .size, .type). A FileList is array-like, not an array, so spread it into a real array with [...files] before you map over it. We reset the highlight, clear the depth counter, and hand the files to one shared handleFiles() — the same function the click-to-browse path will call, so both routes converge on identical logic.
    
        
    zone.addEventListener("drop", e => {
  depth = 0;
  zone.classList.remove("dz-over");
  handleFiles(e.dataTransfer.files);   // a FileList of File objects
});

function handleFiles(fileList) {
  [...fileList].forEach(addFile);      // spread: FileList → real array
  render();
}
    
      
    5. 
      
  5. 
        
    5
    Click-to-browse — the hidden input fallback
    
        
    Dragging is fine on a desktop but hopeless on a phone and awkward with a trackpad, so every real dropzone doubles as a plain file picker. You can't style a native file input, so we hide the real one and forward clicks: clicking the box calls picker.click(), which opens the OS dialog; when files are chosen the input's change fires and we push picker.files through the very same handleFiles(). Reset picker.value = "" afterwards so picking the same file twice still triggers change. Wire Enter/Space on the box too, since it's keyboard-focusable.
    
        
    const picker = document.getElementById("picker");

zone.addEventListener("click", () => picker.click());   // box → dialog
zone.addEventListener("keydown", e => {
  if (e.key === "Enter" || e.key === " ") { e.preventDefault(); picker.click(); }
});

picker.addEventListener("change", () => {
  handleFiles(picker.files);   // SAME path as drop
  picker.value = "";           // so re-picking the same file still fires
});
    
      
    6. 
      
  6. 
        
    6
    Validate — type + size, with a reason
    
        
    Never trust what gets dropped. Check the File.type (a MIME string like image/png) against an allow-list, and fall back to the file extension because some files arrive with an empty type. Check File.size (in bytes) against a maximum. The important UX detail: a rejected file should not silently disappear — return a human reason ("Unsupported type", "Too large — 5 MB max") and show it on the row, so the user knows what to fix. Note this is client-side convenience only; a real server must re-validate.
    
        
    const OK_MIME = /^image\/(png|jpe?g|gif|webp|svg\+xml)$|^application\/pdf$/;
const OK_EXT  = ["png","jpg","jpeg","gif","webp","svg","pdf"];
const MAX     = 5 * 1024 * 1024;           // 5 MB in bytes

function validate(file) {
  const ext = (file.name.split(".").pop() || "").toLowerCase();
  const typeOk = OK_MIME.test(file.type) || OK_EXT.includes(ext);
  if (!typeOk)          return "Unsupported type — images or PDF only";
  if (file.size > MAX)  return "Too large — 5 MB max";
  if (file.size === 0)  return "Empty file";
  return null;                              // null === valid
}
    
      
    7. 
      
  7. 
        
    7
    State is the source of truth — add & render
    
        
    Keep every file the widget knows about in one items array of plain objects, and render the list from it — never poke the DOM directly. Each entry carries the raw File, its display fields, a status ("uploading" | "done" | "error"), a progress number, and a slot for a thumbnail. A stable id lets a remove button find its object later. Format the byte count into KB/MB for humans. Every later feature — progress, thumbnails, removal — is just an edit to this array followed by a re-render.
    
        
    let items = [], seq = 0;

function addFile(file) {
  const error = validate(file);
  items.push({
    id: ++seq, file, name: file.name, size: file.size,
    status: error ? "error" : "uploading",
    error, progress: 0, thumb: null,
    isImage: /^image\//.test(file.type) && file.type !== "image/svg+xml"
  });
}
function fmtSize(b) {
  if (b < 1024)        return b + " B";
  if (b < 1048576)     return (b / 1024).toFixed(1) + " KB";
  return (b / 1048576).toFixed(2) + " MB";
}

  8. 
        
    8
    Progress bar — the simulated upload
    
        
    In a real app you'd send the file with fetch and read XMLHttpRequest.upload.onprogress for the real byte-count; here we simulate it with a timer so the UI is complete and honest about what it represents. On a valid file, start an interval that bumps progress toward 100, re-rendering each tick so the bar animates; when it reaches 100 flip status to "done" and clear the timer. Keep the timers keyed by id so removing a file mid-upload can cancel its timer — no orphaned intervals writing to a row that's gone.
    
        
    const timers = {};

function startUpload(it) {                   // swap for real fetch/XHR progress
  timers[it.id] = setInterval(() => {
    it.progress = Math.min(100, it.progress + 6 + Math.random() * 10);
    if (it.progress >= 100) {
      it.progress = 100; it.status = "done";
      clearInterval(timers[it.id]); delete timers[it.id];
    }
    render();
  }, 120);
}
// <div class="dz-bar"><div class="dz-fill" style="width:${it.progress}%"></div></div>

  9. 
        
    9
    Thumbnails — preview images with FileReader
    
        
    You can show an image before it's uploaded anywhere, because the file's bytes are already in the browser. A FileReader reads a File and, with readAsDataURL, hands you a data: URL you can drop straight into an <img src>. It's asynchronous — the result arrives in onload — so store it on the item and re-render when it lands. (For big images URL.createObjectURL(file) is lighter, but then you must revokeObjectURL to avoid a leak; readAsDataURL is the simplest correct choice here.) Non-images just show an extension badge.
    
        
    function loadThumb(it) {
  if (!it.isImage) return;                   // only images get a preview
  const reader = new FileReader();
  reader.onload = e => { it.thumb = e.target.result; render(); };
  reader.readAsDataURL(it.file);             // → "data:image/png;base64,…"
}
// in render(): it.thumb
//   ? `<img class="thumb" src="${it.thumb}">`
//   : `<span class="ext">${ext.toUpperCase()}</span>`

  10. 
        
    10
    Remove — ✕ a file, and re-render from state
    
        
    Each row gets a ✕ button carrying its file's data-id. Because the list is rendered fresh every time, don't bind a handler per button — use one delegated listener on the container that reads the id off the clicked button. Removing means: cancel that file's upload timer if it's still running, filter it out of the items array, and re-render. The array is the single source of truth, so the DOM and the data can never disagree — and an aria-live line announcing "X added / rejected / removed" keeps it usable without sight.
    
        
    list.addEventListener("click", e => {
  const btn = e.target.closest("[data-id]");
  if (!btn) return;
  removeItem(+btn.dataset.id);
});
function removeItem(id) {
  if (timers[id]) { clearInterval(timers[id]); delete timers[id]; }
  items = items.filter(it => it.id !== id);   // edit the array…
  render();                                    // …then re-render
}
