DESIGNFROMZERO · DAY 75

▮ Input mask — the field that writes the spaces in a card number for you. One number to settle after every keystroke, the caret, and the three things everybody tests about the field are it always looks like the mask, it never keeps a character the mask forbids, and typing the number straight in produces the formatted number. Across 25,640 keystrokes enumerated exhaustively on six masks, all three hold for five of these eight implementations — and four of those five are wrong. The most-shipped one puts the caret after the digit the user left it after on 14.8% of keystrokes. Worse, on a full card there are exactly 3 places to stand where Backspace does nothing at all — predictable from the mask alone, with no implementation in the argument, and matched on all six masks. Meanwhile the three the tests do reject are the control, a genuinely broken one, and one that is correct in every way the user can feel and differs from the right answer only in when it draws the space. The control settles what the separators are guilty of: taking them out removes 100.0% of the dead keys and none of the caret errors. 1,416,376 assertions on load. Pure vanilla JavaScript, one file, no build step.

Two coordinate systems, and only one of them is real

A masked field draws characters the user never typed. That single fact splits every position in it into two different numbers. There is the character index — what selectionStart reports, what the browser hands you, what every string operation in your code uses. And there is the digit index — how many digits of the actual number sit to the left of the caret, which is the only thing the person typing has in their head.

In 4242 4242 the caret at character index 4 and the caret at character index 5 have the same digit index, 4. They look identical on screen: one is drawn just left of the space, one just right of it, and at a normal font size that is a difference of a few pixels the user did not choose. Both are reachable by clicking. Both are reachable by arrow keys. A component that cares which one it got is a component that behaves differently depending on where a fingertip landed.

So the caret cannot be judged by its integer value. It has to be judged in digit space, and that is the first thing this page's oracle does: it keeps a plain string of digits and one index into it, it has no idea the mask exists, and it says what a keystroke meant. Backspace means “remove the digit before me”. It does not mean “remove the character before me”, and the gap between those two sentences is the entire subject here.

The component runs second

A controlled input never sees the keystroke first. The browser applies it — splices the typed character in, or takes one character out — and only then does your input handler get to look. By that point the field holds a string that is not shaped like the mask, and the job is to turn it back into one and decide where the caret goes.

Every implementation on this page does the first half identically: strip the value back to digits, cut it to the mask's capacity, re-render. That half is not in dispute and it is why the property everybody tests is nearly free. They differ in the second half only — where the caret lands, and whether they look at what the browser removed.

The key that does nothing

Put the caret just to the right of the space in 4242 |4242… and press Backspace. The browser removes the space. Your handler strips the value to digits — and the digits are exactly what they were, because a space is not a digit. It re-renders. The space comes back. The value is byte-for-byte what it was before the keystroke.

Nothing on screen changed, so nothing looks broken. There is no error, no flash, no wrong character. The user pressed a key and the field ignored them. Press it again from the same place and it ignores them again. This is the single most reported bug in masked inputs and it is invisible to every property in the left half of the tables above, because the value is always perfectly well formed — it is well formed because nothing happened.

The count is not a mystery either. On a full field, walk every caret position: the dead ones are exactly the ones whose left-hand neighbour is a literal and that have at least one digit further left. That is a property of the pattern, so it can be computed before any implementation exists, and the table above does exactly that on all six masks and then checks it.

The phone mask is the one that breaks the symmetry. It has one more dead Delete than dead Backspace, and the extra one is the opening bracket: at the very start of the field there is a literal to the right of the caret and digits beyond it, but nothing at all to its left. Backspace there has nothing to mean; Delete does, and gets ignored.

The fix is a question about the past, not the present

The correct rule cannot be a function of the value the browser handed back, because that value is identical in the working case and the dead one. It has to know what was removed, which means capturing the field's value and selection in beforeinput, before the browser touches it. Then the rule is one sentence: if the delete was collapsed and took out only literal characters, delete the digit the user was aiming at instead — the one before the caret for Backspace, the one after it for Delete.

Nearly everyone writes the Backspace half. Almost nobody writes the Delete half, because almost nobody tests Delete. That is one clause of difference and it is worth a whole implementation in the tables: same caret behaviour, same shape, one direction of one key silently dead.

What the control settles

It is tempting to say the separators are what break the field, and to reach for a design that does not have any. The control mask is that design, run on the identical corpus: sixteen digit slots, no literals, same digits, same caret indices, same keystrokes.

It removes every dead key. Not most of them — all of them, on every rule, exactly as the closed form says it must, because the closed form counts literals and there are none. That half of the story is completely confirmed.

And it does essentially nothing for the caret. The most-shipped rule is right about the caret on 13.1% of keystrokes with separators and 13.3% without: the separators were never what was breaking it. What breaks it is that the field re-renders at all, and re-rendering throws away the caret whether or not there is a space in the string. A field with no mask and a handler that reformats is still a field that loses your place.

Two implementations the tests reject, and only one of them deserves it

The three blind properties are not useless. They catch one genuinely broken rule — the one that keeps the browser's character index — because on the very first test anybody writes, typing the number straight in, its caret drifts by one at every group boundary and the digits come out scrambled.

They also reject the control, which is correct and does not pretend otherwise: it does not format, so of course typing a number into it does not produce a formatted number. That is what a control is for.

And they reject one implementation that is right in every way a person can feel. Drawing the separator the moment its group fills — showing 4242 with the space already there, waiting — makes the value differ from the strict rendering of its own digits, so the shape property fails on it. Its digits and its caret are identical to the correct rule's on every keystroke in the sweep; only the picture differs, and only sometimes. Whether that counts as a defect is a design decision, and the one property everybody asserts has quietly made it for you.

Two things I set out to show that were not there

The first: I expected that adding rejected keystrokes to the session corpus — typing the separator yourself, which is exactly how people type an expiry date, or fat-fingering a letter — would change which implementation looked better, because rejected characters are the one case that pulls the character index away from the digit index without changing a digit. It changes the percentages and reorders nothing at all: zero of the ordered pairs flip.

The second: I expected per-keystroke accuracy and end-of-session correctness to agree about the ranking, so that either measurement would do. They disagree about exactly one pair — and it is the pair a team is actually choosing between. Keeping the distance from the end of the string is the better rule keystroke for keystroke and the worse one across a whole session, because its errors land on the digit inserts that a session is made of, while the other rule's errors land on keystrokes a session mostly does not contain.

The measurement is an enumeration

Nothing on this page is sampled. Every digit string in the corpus covers every length from empty to full; every caret index in every one of those strings is visited; both character positions that share a digit index are visited separately; every kind of keystroke is applied at each of them; and all eight implementations answer all of it. The percentages hold to a tenth of a point when the corpus is grown, which is what saturation looks like.

Build it

Nine steps. Everything between ENGINE:BEGIN and ENGINE:END in this page's one script block is arithmetic over strings and integers — no DOM, no clock, no random source — so the verifier lifts it out of the file and runs it under Node against oracles written on different representations.

1 · A mask is a pattern, not a list of group sizes

Group sizes get you #### #### #### #### and nothing else. A pattern gets you the phone number too, with a two-character literal run in the middle and one at the start, which is where the interesting edge cases live. 

const MASKS = {
  card:  { pat: '#### #### #### ####' },
  phone: { pat: '(###) ###-####' },
  bare:  { pat: '################' }   // the control
};
const capOf  = pat => [...pat].filter(c => c === '#').length;

2 · Render lazily

Hold each literal back until a digit has arrived to sit after it. An empty phone field should be empty, not a lone opening bracket the user has to delete. 

function render(pat, d){
  let out = '', k = 0, pend = '';
  for (const c of pat){
    if (c === '#'){ if (k >= d.length) break; out += pend; pend = ''; out += d[k++]; }
    else pend += c;
  }
  return out;
}

3 · Write both maps between the two coordinate systems

digitsBefore goes down to digit space, caretForDigit comes back up. They must be inverse for every position; the self-check asserts that rather than trusting it. 

const digitsBefore = (v, pos) =>
  [...v.slice(0, pos)].filter(isDigit).length;

function caretForDigit(v, k){          // just after the k-th digit
  if (k <= 0){ let i = 0; while (i < v.length && !isDigit(v[i])) i++; return i; }
  let seen = 0;
  for (let i = 0; i < v.length; i++)
    if (isDigit(v[i]) && ++seen === k) return i + 1;
  return v.length;
}

4 · Capture the state before the browser edits it

This is the one thing the correct rule needs and the wrong ones do not have. Without it you cannot tell a Backspace that removed a digit from one that removed a space, because the value you are handed is the same either way. 

let PRE = null;
inp.addEventListener('beforeinput', e => {
  PRE = { value: inp.value, sa: inp.selectionStart, sb: inp.selectionEnd, type: e.inputType };
});

5 · The half nobody disagrees about

Strip to digits, cut to capacity, re-render. Do this and the value is always shaped like the mask, which is why the property everybody tests is nearly free and nearly worthless. 

const d = digitsOf(raw.value).slice(0, cap);
const v = render(pat, d);

6 · Put the caret back by counting digits, never by counting characters

Count the digits to the left of the caret in the string the browser handed you, then find the position after that many digits in the string you are about to show. This fixes every insertion, including a pasted number and a character the mask rejects. 

const k = Math.min(digitsBefore(raw.value, raw.caret), d.length);
return { value: v, caret: caretForDigit(v, k) };

7 · Make the delete mean what it says — in both directions

If the delete was collapsed and removed only literal characters, then nothing happened, and nothing is not what the user asked for. Remove the digit they were aiming at instead. The forward half is the clause that gets left out. 

const rem = removedText(prev, ed);
if (prev.sa === prev.sb && rem.length && digitsOf(rem).length === 0){
  if (ed.kind === 'back' && k > 0){ d = d.slice(0, k-1) + d.slice(k); k -= 1; }
  else if (ed.kind === 'fwd' && k < d.length){ d = d.slice(0, k) + d.slice(k+1); }
}

8 · Judge the caret in digit space

Comparing selectionStart against an expected integer will fail on the position that is visually identical and numerically different, and it will pass a rule that happens to agree with your fixture. Compare digitsBefore(value, caret) against the intent oracle and both placements count as right, which is the honest test and also the stricter one. 

const gotK  = digitsBefore(out.value, out.caret);
const want  = intentStep(cap, d, ka, kb, ed);   // digits only, no mask
const caretOk = gotK === want.k;

9 · Run the whole thing, and run the control beside it

Enumerate: every length, every caret index, both placements, every kind of keystroke, every implementation. Then run the identical corpus against a pattern with no literals in it. The difference between the two columns is what the separators are responsible for — and it turns out to be one of the two defects, not both. 

const KS   = keystrokeSweep(MASK_IDS, SEED, REPS);   // every keystroke, every rule
const PAIR = pairedControl('card', SEED_PAIR, REPS_PAIR);
const FULL = fullFieldScan(prepMask(MASKS.card));   // and the closed form it must match
