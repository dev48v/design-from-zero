Grab a row, drag it, and the rest slide out of the way to show where it lands — let go and the list is really reordered.

A drag-to-reorder (or sortable) list is the thing you use to rank a to-do list, arrange a playlist, or set column order: pick up any row and drop it somewhere else. The craft is entirely in the feel. As you drag, the item you are holding follows your pointer while every other row shifts live to open a gap exactly where the item will land, so you always see the result before you commit. On release, the underlying array is spliced into the new order and the list re-renders to match — the visual and the data never drift apart. It is built on Pointer Events, so the same handful of handlers cover mouse, touch and pen; the movement is pure transform so it stays at 60fps; and it has a proper ↑/↓ keyboard path with ARIA announcements underneath. Try it — drag a row up or down, or focus one and use the arrow keys, and watch the read-out on the right update live.

🔨 Build it yourself

    
A sortable list is a column of rows whose order lives in one array. The layout is nothing; the behaviour is everything: grab a row on pointerdown and capture the pointer, follow it on pointermove, compute the target slot from the distance travelled, shift the other rows live to preview the drop, then on pointerup splice-reorder the array and re-render so the data and the DOM match. Because it is built on Pointer Events, mouse, touch and pen all run the same code — and we add an ↑/↓ keyboard path with ARIA so it is not drag-only. We build all of it from scratch, one piece at a time, no framework and no dependencies.

    
    
      
  1. 
        
    1
    The array is the source of truth — render rows from it
    
        
    Do not treat the DOM as the data. Keep the order in one data array of objects and render the list from it, so DOM order always equals array order. Every row is a real focusable element — role="option", tabindex="0", an aria-label that says its position — and carries a data-id so a handler can find its object. touch-action:none on the row is essential: it tells the browser "this gesture is a drag, not a scroll", so a touch drag does not scroll the page instead.
    
        
    let data = [
  { id:1, title:"Draft the launch email", tag:"Marketing" },
  /* …5 more… */
];
function render(focusId){
  list.innerHTML = data.map((it,i) => `
    <li class="drag-item" role="option" tabindex="0" data-id="${it.id}"
        aria-label="${it.title}, position ${i+1} of ${data.length}">
      <span class="handle" aria-hidden="true">⣿</span>
      <span class="num">${i+1}</span>
      <span class="title">${it.title}</span>
    </li>`).join("");
  if (focusId != null) list.querySelector(`[data-id="${focusId}"]`)?.focus();
}
    
      
    2. 
      
  2. 
        
    2
    Grab it — pointerdown, capture, lift
    
        
    Listen for pointerdown on the list (one delegated handler), find the row with closest(".drag-item"), and open a drag state object: the element, its start index, the pointer's start Y, and the row height including the gap (measured from two real rows so you never hard-code it). Then call setPointerCapture(pointerId) — the single most important line — so every later move and the release are routed to this element even when the pointer leaves it. Add a dragging class to lift it (shadow, raised z-index) and mark the rest as shifting so only they animate.
    
        
    let drag = null;
list.addEventListener("pointerdown", e => {
  const item = e.target.closest(".drag-item");
  if (!item || !e.isPrimary) return;
  const rows = [...list.children];
  const rowH = rows.length > 1
    ? rows[1].getBoundingClientRect().top - rows[0].getBoundingClientRect().top
    : item.offsetHeight;                    // height + gap, measured
  drag = { item, rows, rowH, startIndex: rows.indexOf(item),
           targetIndex: rows.indexOf(item), startY: e.clientY };
  item.setPointerCapture(e.pointerId);      // ← drag survives leaving the row
  item.classList.add("dragging");
  rows.forEach(r => r !== item && r.classList.add("shifting"));
});
    
      
    3. 
      
  3. 
        
    3
    Follow the pointer — pointermove
    
        
    Because we captured the pointer, we can attach pointermove to the dragged element itself. The delta is just dy = e.clientY - startY, and the held row follows by writing transform: translateY(dy). We move it with a transform, not top or margins, so it is composited on the GPU and never triggers layout — that is what keeps a drag buttery. The dragged row deliberately has no transition, so it tracks your finger 1:1; only the other rows animate.
    
        
    item.addEventListener("pointermove", e => {
  if (!drag) return;
  const dy = e.clientY - drag.startY;
  drag.item.style.transform = `translateY(${dy}px)`;   // 1:1, no transition
  updateTarget(dy);                                     // step 4
});
    
      
    4. 
      
  4. 
        
    4
    Where will it land? — the target index from pointer Y
    
        
    This is the heart of it. You do not track the mouse against every row's rectangle — you ask one question: how many whole rows have I travelled? That is Math.round(dy / rowH). Add it to the start index and clamp to the list bounds and you have the target slot. Rounding means the item snaps to a new slot once you have dragged past a row's midpoint — exactly the "it flips when I'm halfway over the next one" feel. Only act when the target actually changes, so you are not re-shifting on every pixel.
    
        
    function updateTarget(dy){
  const n = drag.rows.length;
  const target = Math.max(0, Math.min(n - 1,
    drag.startIndex + Math.round(dy / drag.rowH)));   // whole rows travelled
  if (target !== drag.targetIndex){
    drag.targetIndex = target;
    shiftOthers();                                    // step 5
  }
}
    
      
    5. 
      
  5. 
        
    5
    Open the gap — shift the other rows live
    
        
    Nothing in the array has changed yet — the reorder is still just a preview painted with transforms. Every row between the start slot and the target slot slides by exactly one row-height to make room: when you drag down, the rows you passed slide up; when you drag up, they slide down. Because those rows carry the shifting class (a transform transition), each one glides into place instead of snapping, and the empty slot visibly opens where the item will drop.
    
        
    function shiftOthers(){
  const { rows, startIndex, targetIndex, item, rowH } = drag;
  rows.forEach((r, i) => {
    if (r === item) return;
    let shift = 0;
    if (startIndex < targetIndex && i > startIndex && i <= targetIndex) shift = -rowH; // dragging down
    else if (startIndex > targetIndex && i >= targetIndex && i < startIndex) shift =  rowH; // dragging up
    r.style.transform = shift ? `translateY(${shift}px)` : "";
  });
}
    
      
    6. 
      
  6. 
        
    6
    Drop — splice-reorder the real array
    
        
    On pointerup the preview becomes real. Release the pointer capture, then perform the one operation the whole widget exists for: pull the item out of its start slot and put it back at the target — data.splice(from, 1) then data.splice(to, 0, moved). That is the actual reorder; every transform up to now was theatre. If the target equals the start (you dropped it back), you change nothing — a click, not a move.
    
        
    item.addEventListener("pointerup", e => {
  const { startIndex, targetIndex } = drag;
  item.releasePointerCapture(e.pointerId);
  if (targetIndex !== startIndex){
    const [moved] = data.splice(startIndex, 1);   // pull out
    data.splice(targetIndex, 0, moved);           // put back at target
  }
  const focusId = +item.dataset.id;
  drag = null;
  commit(focusId);                                // step 7
});
    
      
    7. 
      
  7. 
        
    7
    Re-render from the array — and no flash
    
        
    The rows are still wearing preview transforms and the DOM order is still the old order — only the array is new. Fix both in one move: re-render the list from data. The fresh rows are created in the new order with no transforms at all, so they land exactly where the preview left them and there is no visible jump. Re-rendering from the single source of truth is what guarantees the picture and the data can never disagree. Restore focus to the row you moved by its id.
    
        
    function commit(focusId){
  render(focusId);   // rebuild rows from `data` — new order, zero transforms
}
// because the preview already showed the final layout,
// the re-render is seamless: same positions, now backed by real data.
    
      
    8. 
      
  8. 
        
    8
    Keyboard fallback — ↑ / ↓ move the focused row
    
        
    A drag-only list is unusable for keyboard and screen-reader users, and the fix is small because the array is already the source of truth. Focus a row, and ↑/↓ run the exact same splice the drop does — just with indices from the keyboard instead of the pointer — then re-render and keep focus on the moved row so you can move it again. Home/End jump it to the ends. Same reorder logic, a completely different input.
    
        
    list.addEventListener("keydown", e => {
  const item = e.target.closest(".drag-item");
  if (!item) return;
  const rows = [...list.children], i = rows.indexOf(item);
  let j = i;
  if      (e.key === "ArrowUp")   j = i - 1;
  else if (e.key === "ArrowDown") j = i + 1;
  else if (e.key === "Home")      j = 0;
  else if (e.key === "End")       j = rows.length - 1;
  else return;
  e.preventDefault();
  if (j < 0 || j >= rows.length || j === i) return;
  const [moved] = data.splice(i, 1);
  data.splice(j, 0, moved);          // same splice as the drop
  render(moved.id);                  // keep focus on the moved row
});
    
      
    9. 
      
  9. 
        
    9
    ARIA + touch — the honest finish
    
        
    Make it real for everyone. The list is a role="listbox" with an aria-label; each row is a role="option" whose aria-label states "<title>, position N of M". Pipe every meaningful change — picked up, hovering slot k, dropped at k — through one visually-hidden aria-live="assertive" region so a screen-reader user hears the reorder happen. touch-action:none makes the drag work on phones without hijacking scroll, and honouring prefers-reduced-motion (drop the shift transition) keeps it comfortable. None of this changes how it looks — it is the difference between a demo and something you can ship.
    
        
    <ul role="listbox" aria-label="Reorderable task list">
  <li role="option" tabindex="0"
      aria-label="Draft the launch email, position 1 of 6"> … </li>
</ul>
<div id="live" class="sr-only" role="status" aria-live="assertive"></div>

function announce(msg){ live.textContent = msg; }
// pointerdown → announce("Picked up X.")
// updateTarget → announce("Position k of n.")
// drop / key   → announce("X moved to position k of n.")
