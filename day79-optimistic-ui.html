DESIGNFROMZERO · DAY 79

❤️ Optimistic UI — you tap, the heart fills instantly, and the request goes out behind it. If the server disagrees, you roll back. The engine simulates the QUEUE, not a browser: a sequence of taps, a network that reorders and fails, a server with its own truth, and five reconciliation policies over 600 enumerated sessions each, so every figure is a count. 🔴 The rollback everybody writes — undo the toggle when the request fails — is EXACTLY right for a toggle and the WORST option for a set. On a like button it agrees with the server on 600 of 600 sessions. On a set-a-value control it agrees on 219 of 600, which is worse than not rolling back at all (411). The policy did not change. The operation did, and nothing in the UI code knows which one it is holding. 🔴 The careful-looking alternative — restore the value the item had before that tap — is mediocre at both: 396 and 357. It looks more correct and is more wrong, because by the time the failure comes back later taps have already moved the item. 🔴 And every optimistic policy passes every property a test can assert without a server in the room. The suite cannot separate the one that is always right from the one that is right 36% of the time.

Three states, and only one of them is on the screen. What the user meant is their taps in the order they made them. What the server has is the successful requests in the order they arrived, which is not the same order. What the screen shows is whatever the reconciliation policy decided. The page scores the third against the second, because that is the disagreement a user actually runs into.

Five policies, two operations

UNDO-THE-TOGGLE ON A TOGGLE

—

sessions matching the server

THE SAME POLICY ON A SET

—

the policy did not change

NOT ROLLING BACK AT ALL, ON A SET

—

POLICIES PASSING EVERY PROPERTY

of five

1. The rollback is right or wrong depending on the algebra

A toggle is self-inverse — applying it twice is doing nothing — and two toggles on the same item commute. So “undo the toggle” is a correct inverse no matter how many other taps have landed in between, which is why it scores perfectly.

A set is neither. Undoing set to blue by toggling is not an operation that means anything, and the value the item had before that tap is not the value it should return to once three later taps have happened.

🔴 The same five lines of code, scored on two controls that look identical on screen. The policy that is exactly right for one is the worst of the five for the other — and worse than doing nothing. Rollback correctness is a property of the operation, not of the rollback.

2. The careful-looking one is worse at both

Restoring “the value it had before that tap” sounds strictly more principled than toggling — it remembers something. What it remembers is stale: the failure arrives after later taps have already moved the item, so the restored value belongs to a state that no longer exists. It reverts those later taps too, silently, and it does that on both operations.

3. The properties cannot see any of it

Here is what a test can assert with no server and no user: the screen changes before the request resolves, the screen stops changing once everything has resolved, and an item does not move twice for one successful tap.

Every optimistic policy passes all three, including the one that ends up disagreeing with the server on two sessions in three. The only policy that fails is the pessimistic one, and it fails on instant — which is the property it is deliberately not trying to satisfy. A suite built from these three assertions rejects the safest option and accepts the worst.

4. And with no failures, nothing can be told apart

On a toggle, a 0% failure rate makes every policy agree on all 600 sessions. A fixture with a reliable network is not a weak test of reconciliation — it is no test of it at all, and it is the fixture most suites have.

🔴 On a set it is not even that kind. With zero failures the optimistic policies still disagree with the server on 138 of 600 sessions, because reordering by itself is enough: the last write to arrive wins at the server, the last tap wins on screen, and those are different requests. Toggles commute, so order cannot hurt them. Sets do not. A reliable network removes the whole problem for one control and leaves most of it standing for the other.

What this models and what it does not

Requests reorder and fail; the server applies what arrives, in arrival order. The failure rates and the latency spread are declared and set by the controls above, not measured from anything real, so the exact percentages belong to those settings. What does not depend on them: a toggle is self-inverse and a set is not, so one inverse is correct and the other is not, at any failure rate above zero. Out of scope, each of which makes reconciliation harder: retries, requests that are applied but never acknowledged, and two clients editing the same item.

How it works

// the whole finding, in one line
const applyTo = (st, a) => { st[a.item] = a.op === "set" ? a.value : !st[a.item]; };

// "undo the toggle" - a correct inverse for one of those, and not the other
for (const a of arrivals) if (a.fails) st[a.item] = !st[a.item];

The draws come from a seeded Park-Miller generator rather than Math.random, so every session is reproducible and a verifier can re-derive the same 600. The draw below n takes the high bits — (next() * n) >>> 31 would be wrong in JavaScript, because bitwise operands are coerced to 32 bits and the product overflows that for any n above 1.
